## 피드백 내역

#### 피드백 배경

##### 2026-08-14

- 이은경 학생의 `웹사이트/설계` 폴더를 기준 사례로 삼아 이지희 학생의 `자동화` 폴더 구조와 결과물을 비교 분석했습니다.
- 이은경 설계 폴더는 클라이언트별로 사이트맵, 서비스 흐름도와 화면 설계서를 분리하고 각 단계의 결과물을 일정한 파일 세트로 관리합니다.
- 이지희 자동화 폴더는 브랜드 기본 자료부터 리서치, 클라이언트, 설계·스토리보드와 로고까지 작업 범위가 넓고 산출물 수도 많지만, 대량 생성 이후 번호·이름·참조 파일과 최종 결과물의 연결 검증이 충분히 이루어지지 않았습니다.
- 이번 검토는 파일 존재 여부, 폴더 구조, 파일명 규칙, 문서 내부 참조, 단계별 산출물 수, 대표 HTML의 시맨틱 구조와 명세 반영 여부를 기준으로 진행했습니다.
- 학생은 답변을 기다리는 동안 기존 클라이언트로 화면 설계서를 생성했으며, 해당 결과를 버릴지 하나의 스토리보드로 병합할지 질문했습니다.
- 강사는 기존 결과를 우선 삭제하지 않고 남겨둔 상태에서 안내한 수정 기준대로 다시 진행하도록 했습니다.
- 학생은 가상 클라이언트 생성 skill의 `필수 UI 구성요소`가 모든 클라이언트의 요구사항과 화면을 동일하게 만든 원인인지 질문했습니다.
- 강사는 클라이언트 파일에서 구성요소 관련 내용을 모두 제거하고 목적과 니즈 중심으로 작성하도록 안내했습니다.

#### 비교 기준에서 확인한 좋은 점

- 가상 클라이언트 20명과 각 클라이언트 분석·사이트 분석 문서를 마련해 다양한 사용자 요구를 설계 입력으로 사용하려는 시도가 확인됩니다.
- 서비스 흐름도는 20명 각각에 대해 목적 1~5의 `.md`, `.mmd`, `.svg` 세트가 존재하여, 파일 수 기준으로는 100개 목적별 흐름 세트가 구성되어 있습니다.
- 사이트맵과 서비스 흐름도에 목적별 사용 사례를 구분하고 정상 흐름뿐 아니라 오류·이탈·재진입과 같은 예외 상황을 포함하려는 설계 방향이 좋습니다.
- 차은채 화면 설계서에는 상품 큐레이션, 장바구니, 찜, 타이머, 구독, 선물과 브랜드 소개 등 화면 기능을 구체적으로 명세하려는 노력이 확인됩니다.
- 스토리보드 문서에는 섹션 ID, 목적, UI 요소, 데이터, 사용자 행동, 시스템 처리, 이동 대상과 상태 변화를 표로 연결하려는 구조가 있습니다.
- 결과물을 문서형 `.md`, Mermaid 원본 `.mmd`, 벡터 결과 `.svg`, 구현 확인용 `.html`, 데이터용 `.json`으로 나누려는 방향은 자동화 파이프라인의 확장성 측면에서 장점입니다.
- 로고 결과물을 다수 생성하고 레퍼런스와 프롬프트 기록을 함께 보관하여 시각 탐색 과정의 흔적을 남긴 점은 좋습니다.

#### 핵심 문제 분석

##### 2026-08-14

###### 1. 클라이언트 번호와 이름이 사이트맵 파일에서 일치하지 않음

- 원본 가상 클라이언트는 `01 차은채`, `02 신유진`, `03 윤서연`, `04 최하은`, `05 임태경`, `06 권명수`, `07 송아린`, `08 이도은`, `09 박지후`, `10 이지민`, `11 윤기준`, `12 서지안` 순서입니다.
- 그러나 사이트맵에서는 차은채가 `사이트맵3_차은채`, 신유진이 `사이트맵4_신유진`, 윤서연이 `사이트맵5_윤서연`, 윤기준이 `사이트맵2_윤기준`으로 저장되어 원본 번호와 다릅니다.
- 권명수는 원본 번호가 06이지만 `사이트맵7_권명수`, 서지안은 원본 번호가 12이지만 `사이트맵15_서지안`으로 저장되어 있습니다.
- 최하은은 `사이트맵4_최하은`과 `사이트맵6_최하은`이 동시에 존재하고, 번호 4에는 신유진과 최하은, 번호 5에는 윤서연과 임태경, 번호 7에는 권명수와 송아린, 번호 15에는 서지안과 한명석이 함께 존재합니다.
- 이 상태에서는 번호만으로 입력 클라이언트와 결과물을 연결할 수 없고, 다음 자동화 단계가 다른 사람의 사이트맵을 읽을 위험이 큽니다.

###### 2. 사이트맵과 서비스 흐름도의 참조 파일이 서로 연결되지 않음

- 차은채 사이트맵 실제 파일은 `사이트맵3_차은채_목적1_브랜딩탐색.md`인데 서비스 흐름도 문서는 `사이트맵1_차은채_목적1_브랜딩탐색.md`를 기준 문서로 적고 있습니다.
- 즉 서비스 흐름도 내부에서 참조하는 상위 사이트맵 파일이 실제 폴더에 존재하지 않습니다.
- 마스터 규칙은 사이트맵과 서비스 흐름도의 화면·단계 라벨을 1:1로 동기화하도록 정의하지만, 파일 단계에서부터 1:1 연결이 깨져 있어 라벨 동기화 여부를 신뢰하기 어렵습니다.
- 사이트맵과 서비스 흐름도의 번호 체계가 서로 달라 자동으로 병합하면 잘못된 입력을 선택하거나 파일을 찾지 못할 수 있습니다.

###### 3. 동일 인물의 기본 정보가 문서마다 달라짐

- 차은채 사이트맵은 `29세 WICKETA 총괄 디렉터`로 설명하지만 서비스 흐름도와 화면 설계서는 `34세 WICKETA 디렉터`로 설명합니다.
- 같은 클라이언트의 나이, 역할, 프로젝트 목표와 핵심 기능이 단계별로 달라지면 후속 화면 설계가 어느 요구사항을 근거로 했는지 판단할 수 없습니다.
- 각 산출물에 입력 파일명과 클라이언트 ID를 기록하고도 내용이 달라졌으므로 자동 생성 전 입력 잠금과 생성 후 일치 검사가 필요합니다.

###### 4. 사이트맵 파일이 규칙보다 많고 중복·오배치되어 있음

- 마스터 규칙은 클라이언트 20명에게 목적별 사이트맵 5세트를 생성하므로 `.md` 기준 100개 목적별 파일이 예상됩니다.
- 실제 사이트맵 폴더에는 목적별 인물 조합이 21세트로 확인되어 `.md` 목적별 파일만 105개이며, 별도의 통합 사이트맵 17개까지 포함해 `.md`, `.mmd`, `.svg`가 각각 122개 존재합니다.
- 파일 수가 많다는 사실이 완성도를 의미하지 않으며, 현재는 중복 번호와 잘못된 이름 때문에 어떤 100개가 정상 최종본인지 구분하기 어렵습니다.
- 이은경 설계 폴더처럼 `사이트맵/[클라이언트명]/사이트맵.md·mmd·svg·png` 구조로 묶이지 않고 한 폴더에 366개 파일이 평면적으로 저장되어 검수와 유지보수가 어렵습니다.

###### 5. 상위 단계는 20명분인데 화면 설계서와 스토리보드는 거의 완성되지 않음

- 서비스 흐름도는 20명×5목적까지 생성됐지만 `화면 설계서`의 자동화 결과는 차은채용 `화면_설계서_차은채.md`, `화면_목록_차은채.json`, `와이어프레임_차은채.html` 1세트만 확인됩니다.
- 별도의 `수업시간 화면설계서`에는 서지안 관련 파일이 있으나 자동화 파이프라인의 20명 결과와 같은 규칙으로 연결되어 있지 않습니다.
- `스토리보드 결과` 역시 차은채용 `.md`, `.html`, `.json` 1세트만 확인됩니다.
- 따라서 현재 파이프라인은 사이트맵과 서비스 흐름도 대량 생성에서 멈췄고, 20명 전체가 화면 설계서와 스토리보드까지 완료된 상태가 아닙니다.
- 자동 순차 진행 문구가 있더라도 실제 완료 현황표가 없어 어느 클라이언트가 어느 단계까지 끝났는지 바로 판단할 수 없습니다.

###### 6. 스토리보드가 존재하지 않는 화면 설계서 파일을 결합했다고 기록함

- `스토리보드01_차은채.md`는 목적별 `화면설계서01_차은채_목적1~5` 파일을 상위 산출물로 표기합니다.
- 실제 화면 설계서 폴더에는 해당 목적별 화면 설계서 5개가 존재하지 않고, 통합형 `화면_설계서_차은채.md` 1개만 있습니다.
- 스토리보드 문서에는 “총 15종 100% 결합”, “100% 완벽히 결합”이라고 적혀 있지만 실제 입력 파일 존재 여부와 맞지 않습니다.
- 완료 표현은 파일 존재, 참조 일치, 요구사항 추적과 구현 검증을 통과한 뒤에만 사용해야 합니다.

###### 7. 산출물 명세 자체가 서로 충돌함

- 화면 설계서는 메인페이지에 상품 큐레이션 `SEC-01~SEC-20` 20개를 명세합니다.
- 마스터 스토리보드 규칙과 차은채 스토리보드는 `SEC-01~SEC-15` 15개 섹션을 기준으로 작성합니다.
- 같은 파이프라인 안에서 15개와 20개 기준이 충돌하므로 어떤 문서가 최종 기준인지 확정할 수 없습니다.
- 섹션 ID가 후속 HTML, JSON과 연결되므로 기준 수량을 하나로 고정하고 모든 문서와 코드에서 동일하게 검증해야 합니다.

###### 8. 절대 경로가 현재 작업공간과 맞지 않아 재사용성이 낮음

- `CLAUDE.md`와 화면 설계서는 `C:\UIUX이지희\Antigravity\자동화\...` 경로를 입력·출력 위치로 고정합니다.
- 실제 검토 위치는 `C:\Users\SBS\Documents\GitHub\UIUXA_Work\UIUX\work\이지희\자동화\...`이므로 문서의 절대 경로가 현재 폴더와 일치하지 않습니다.
- 화면 설계서의 HTML 링크도 `file:///C:/UIUX이지희/Antigravity/...`를 사용해 다른 PC나 현재 저장소에서 바로 열리지 않습니다.
- 자동화 문서는 실행 위치를 기준으로 상대 경로를 계산하고, 결과 문서 내부 링크도 상대 경로로 작성해야 합니다.

###### 9. 문서 접근성 명세와 실제 HTML 구현이 일치하지 않음

- 차은채 스토리보드는 동적 상태에 `aria-live="polite"`를 사용하고 모든 입력에 명시적 `<label>`을 제공한다고 명세합니다.
- 실제 `스토리보드01_차은채.html`에서는 `aria-` 속성이 확인되지 않고 `<label>`은 1개만 확인됩니다.
- `와이어프레임_차은채.html`에서도 `aria-` 속성과 `<label>`이 확인되지 않습니다.
- 차은채 화면 설계 HTML은 `<h1>`이 없고 두 HTML 모두 `<section>` 요소가 없어 문서에서 정의한 화면 위계와 랜드마크가 실제 마크업에 충분히 반영되지 않았습니다.
- 버튼 수는 많지만 폼 구조가 없고, 버튼의 이름·상태·키보드 조작·포커스 이동·오류 안내가 실제로 작동하는지 별도 검증이 필요합니다.

###### 10. 설계 결과의 시각 확인용 파일 세트가 부족함

- 이은경 설계 결과는 사이트맵과 서비스 흐름도마다 `.md`, `.mmd`, `.svg`, `.png`를 함께 제공하고, 화면 설계서는 `.md`, `.json`, `.html`, `.svg`, `.png`, `.pdf`까지 제공합니다.
- 이지희 사이트맵과 서비스 흐름도에는 `.md`, `.mmd`, `.svg`는 있지만 검토자가 빠르게 확인할 `.png`가 없습니다.
- 화면 설계서에는 `.svg`, `.png`, `.pdf`가 없어 HTML을 실행하지 않으면 정적 검토와 제출 확인이 어렵습니다.
- 필수 형식을 무조건 늘리기보다 제출·검수에 필요한 대표 이미지와 PDF 여부를 정하고 일관되게 출력해야 합니다.

###### 11. 자동화 실행 파일과 결과물·의존성이 한 폴더에 혼재함

## 누적 총요약

이지희 학생은 WICKETA 프로젝트를 브랜드 기획, 리서치, 가상 클라이언트, 설계, 스토리보드와 로고까지 넓은 자동화 범위로 확장했습니다. 20명의 클라이언트와 목적별 사이트맵·서비스 흐름도를 대량 생성하고, 문서·Mermaid·SVG·HTML·JSON으로 결과 형식을 나누려는 시도는 강점입니다. 특히 목적별 사용자 흐름, 예외 상황, 상품 큐레이션과 상태 변화를 구체적으로 명세하려는 설계 역량이 확인됩니다.

현재 가장 큰 문제는 산출물의 양이 아니라 **단계 간 추적 가능성과 최종 완결성**입니다. 원본 클라이언트 번호와 사이트맵 번호가 다르고, 같은 번호에 여러 이름이 존재하며, 서비스 흐름도가 실제로 없는 사이트맵을 참조합니다. 차은채의 나이도 문서별로 29세와 34세로 다르고, 스토리보드는 존재하지 않는 목적별 화면 설계서 5개를 100% 결합했다고 기록합니다. 화면 설계서의 20개 섹션과 스토리보드의 15개 섹션 기준도 충돌합니다.

또한 사이트맵과 서비스 흐름도는 20명 규모로 생성됐지만 화면 설계서와 스토리보드는 차은채 중심의 1세트만 확인되어 파이프라인이 끝까지 완성되지 않았습니다. HTML은 문서에서 접근성을 상세히 약속하지만 실제 마크업에는 `section`, `form`, `aria-` 속성과 연결된 레이블이 부족합니다. 절대 경로, 캐시·로그·의존성 혼재와 완료 현황표 부재도 재실행과 검수를 어렵게 만듭니다.

수정 작업에서는 기존 자동화 폴더를 보존하고 `최종 수정 파일`에 20명 전체의 새 결과를 생성했습니다. 클라이언트 매니페스트를 단일 기준으로 사용하고, 각 클라이언트별 사이트맵 4종·서비스 흐름도 4종·화면 설계서 6종을 동일한 폴더 규칙으로 구성했습니다. 결과 내용은 이은경 학생의 SOAPHE 구조를 따르지 않고 WICKETA의 감정 진단·믹솔로지·리추얼·번들·커뮤니티 경험을 중심으로 재구성했습니다. 20개의 고유 콘셉트, 5개 레이아웃 유형, 클라이언트별 화면 ID, 12개 경험 모듈과 상품 20개를 적용했으며 PNG와 PDF도 다시 생성했습니다. 자동 검증 567개 항목은 오류 없이 통과했습니다.

추가 지도에서는 기존 화면 설계서를 버리지 않고 수정 전 참고 자료로 남기되, 현재 상태 그대로 하나의 스토리보드로 병합하지 않도록 안내했습니다. 모든 클라이언트 결과가 비슷해진 핵심 원인으로 가상 클라이언트 생성 skill의 필수 UI 구성요소 규칙이 확인되었습니다. 클라이언트 파일에서는 GNB, 3D 뷰어, 타이머, 감정 다이얼, 장바구니 드로어, 스크롤 복원과 FAQ 같은 화면 해결책을 제거하고 목적·니즈·문제·판단 기준·성공 조건과 제약만 유지해야 합니다. 수정한 클라이언트를 기준으로 요구사항 분석과 설계를 다시 실행한 뒤 클라이언트별 차이가 확인되었을 때 공통 기능과 고유 기능을 최종 병합합니다.

다음 검토에서는 새 결과의 파일 완결성보다 실제 콘텐츠 품질을 중심으로 확인합니다. 클라이언트별 특화 초점이 화면 카피와 기능에 충분히 차별화되었는지, 20개 상품의 분산 배치가 각 인물의 목표에 맞는지, 대표 인터랙션이 실제 사용자 테스트에서 이해되는지, 최종 로고 선택안이 화면에 반영되는지를 우선 확인합니다.
