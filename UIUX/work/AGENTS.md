# 학생 피드백 기록 자동화 지침

## 목적

이 작업공간의 학생별 `피드백[학생이름].md`는 강사가 학생과 나눈 대화, 지도 내용, 제출물 검토 결과와 다음 확인 사항을 장기간 기억하기 위한 누적 기록이다. 새 대화나 파일이 제공되면 기존 기록을 보존하면서 날짜별 내역을 추가하고, 파일 마지막의 누적 총요약을 최신 상태로 갱신한다.

## 대상 파일

- 학생 폴더: `[학생이름]/`
- 피드백 파일: `[학생이름]/피드백[학생이름].md`
- 학생 이름은 사용자가 명시한 이름을 우선한다.
- 카카오톡 대화명이 폴더명과 다르면 사용자가 알려준 대응 관계를 따른다.

## 표준 문서 구조

모든 학생 피드백 파일은 아래 순서를 사용한다.

```markdown
# [학생이름] 학생 피드백 기록

> 기록 목적

## 기본 정보

## 피드백 내역

#### 피드백 배경
##### YYYY-MM-DD

#### 사용한 참고 링크
##### YYYY-MM-DD

#### 강사 피드백
##### YYYY-MM-DD

#### 학생의 질문·반응 및 이해도
##### YYYY-MM-DD

#### 작업 수정 지침
##### YYYY-MM-DD

#### 제출물 검토 메모
##### YYYY-MM-DD

#### 다음 확인 사항
##### YYYY-MM-DD

---

## 누적 총요약
```

상황에 맞지 않는 하위 항목은 생략할 수 있지만 `피드백 내역`과 문서 마지막의 `누적 총요약`은 반드시 유지한다.

피드백은 날짜를 최상위 기준으로 묶지 않는다. `#### 피드백 배경`, `#### 강사 피드백`처럼 내용의 종류를 대제목으로 먼저 구분하고, 각 대제목 아래에서 `##### YYYY-MM-DD` 형식으로 날짜별 내용을 오름차순 정리한다.

`권장 화면 흐름`은 표준 항목으로 생성하지 않는다. 대화에서 강사가 화면 순서 자체를 명시한 경우에도 별도 권장안을 확장하지 말고, 실제 발언 범위 안에서 `강사 피드백` 또는 `작업 수정 지침`에 간략히 기록한다.

## 모든 학생 파일 적용 원칙

- 이 지침은 특정 학생에게만 적용하지 않고 작업공간의 모든 `[학생이름]/피드백[학생이름].md`에 동일하게 적용한다.
- 새 대화가 들어온 학생의 파일부터 표준 구조로 정리한다.
- 기존 파일이 과거 형식이더라도 내용을 삭제하지 않고 적절한 날짜 기록 또는 기본 정보로 이동한다.
- 날짜를 확인할 수 없는 기존 검토 내용은 임의의 날짜를 붙이지 않고 `### 날짜 미상` 아래에 보존한다.
- 제출물이 없는 학생의 기존 안내도 삭제하지 않고 `제출물 검토 메모`에 보존한다.
- 사용자가 전체 학생 파일의 일괄 정리를 요청한 경우에만 모든 파일을 한 번에 변환한다.

## 입력 처리 파이프라인

## 학생 답장 문장 작성 모드

사용자가 학생에게 피드백하고 싶은 문장이나 메모를 보내며 답장 작성을 요청하면, 파일 기록 작업과 구분하여 다음 규칙을 적용한다.

답장 작성 전 루트의 `Wireframe.md`를 읽고 학생별 현재 상태와 상황별 피드백 기준에서 관련 내용을 찾는다. 특정 학생의 최신 맥락이 필요하면 해당 학생의 `피드백[학생이름].md`도 확인한다. 두 파일의 내용이 다르면 날짜별 원본 기록인 학생별 피드백 파일을 우선한다.

1. 사용자가 보낸 문장의 말투, 높임말 수준, 문장 길이, 이모티콘 사용 여부와 친근한 정도를 우선 파악한다.
2. 핵심 의미와 지도 방향은 바꾸지 않고, 학생이 바로 이해하고 실행할 수 있도록 자연스럽게 다듬는다.
3. 사용자가 쓰지 않은 과도한 칭찬, 평가, 전문 용어, 새로운 과제나 요구사항을 임의로 추가하지 않는다.
4. 학생에게 그대로 복사해 보낼 수 있는 완성된 답장 문장만 우선 제공한다.
5. 사용자가 여러 내용을 보내면 관련 내용을 자연스러운 순서로 연결하되 지나치게 길게 설명하지 않는다.
6. 수정 요청, 유지할 내용과 다음 행동이 함께 있으면 서로 혼동되지 않도록 명확하게 표현한다.
7. 원문이 짧고 구어체이면 답장도 짧고 구어체로 작성한다. 원문이 정중하고 상세하면 같은 수준으로 맞춘다.
8. 원문의 오탈자나 어색한 표현은 자연스럽게 고치되 강사 고유의 말투는 유지한다.
9. 학생 이름이 제공되면 필요할 때만 자연스럽게 호칭에 사용한다.
10. 사용자가 특별히 요청하지 않는 한 해설, 작성 이유, 여러 버전이나 제목을 덧붙이지 않는다.
11. `Wireframe.md`에서 관련 기준을 찾더라도 사용자가 보낸 문장의 범위를 넘어 새로운 지시를 임의로 추가하지 않는다.
12. 학생 피드백에 `Hero`, `CTA`, `GNB`, `UI`, `UX`, `모달`, `반응형`, `접근성`처럼 학생이 바로 이해하기 어려울 수 있는 영문·전문 용어를 사용할 때는 용어만 단독으로 쓰지 않는다. 처음 등장할 때 `Hero(웹사이트에 들어갔을 때 가장 먼저 보이는 상단 대표 영역)`처럼 쉬운 우리말과 화면에서의 역할을 함께 설명한다.
13. 전문 용어를 쉬운 표현으로 바꿔도 의미가 유지되면 `메인페이지 첫 화면`, `이동·신청 버튼`, `상단 메뉴`, `팝업창`처럼 학생이 작업 파일에서 바로 찾을 수 있는 표현을 우선 사용한다. 전문 용어가 꼭 필요하면 쉬운 설명을 먼저 쓰고 용어는 괄호 안에 보조적으로 표기한다.
14. 설명은 사전식 정의로 끝내지 않고 `화면의 어느 부분인지`, `왜 수정해야 하는지`, `어떻게 바꾸면 되는지`를 학생의 실제 결과물과 연결해 작성한다.

### 강사 실제 말투 프로필

학생에게 바로 보내는 답장이나 피드백 문장은 아래 말투를 기본으로 하되, 사용자가 제공한 원문의 높임말 수준과 분위기가 다르면 원문을 우선한다.

- 기본 말투는 친근한 반말형 코칭 말투로 작성하고 `~해줘`, `~하면 돼`, `~해야 해`, `~인 상태야`, `~보여주면 됨`, `~될듯`과 같은 어미를 자연스럽게 사용한다.
- 학생 이름이 있으면 답장 첫 부분처럼 필요한 위치에서만 `민경아`, `지민아`와 같이 자연스럽게 부르고 문단마다 반복하지 않는다.
- 피드백은 가능하면 `현재 결과에서 잘된 부분 확인 → 유지할 내용 지정 → 다만 또는 현재로 문제 설명 → 구체적인 수정 방법 → 진행 순서 → 정리`의 흐름으로 작성한다.
- 잘된 부분은 `잘 잡혀 있어`, `많이 반영됐어`, `이 방향은 유지하면 돼`처럼 확인된 결과를 근거로 짧게 인정하고 과도한 칭찬은 추가하지 않는다.
- 수정할 부분을 전달할 때는 `다만`, `그런데`, `현재는`, `먼저`, `그다음`과 같은 연결어를 사용해 이유와 순서를 자연스럽게 이어 준다.
- 기존 작업을 유지할 수 있는 경우 `기존 내용을 빼거나 처음부터 다시 만들 필요는 없어`, `이 부분은 유지하면 돼`처럼 먼저 안심시킨 뒤 수정 범위를 알려 준다.
- 명령만 나열하지 않고 파일명, 화면 위치, 상품 수, 화면 크기, 섹션, 버튼과 상태처럼 학생이 실제 결과물에서 바로 찾을 수 있는 근거를 함께 제시한다.
- 수정 지시는 강압적인 표현보다 `수정해 줘`, `먼저 확인하면 돼`, `정리해서 다시 보여줘`처럼 부드럽지만 행동이 분명한 표현을 사용한다.
- 내용이 많으면 `[유지]`, `[수정]`, `[진행 순서]` 또는 번호 목록으로 구분하고 각 항목은 학생이 바로 실행할 수 있는 작업 단위로 작성한다.
- 마지막에는 필요할 때 `정리하면`, `정리하자면`, `최종 정리하면`으로 핵심 유지 사항과 다음 행동을 짧게 다시 묶는다.
- `~엉`, `~행`, `~둡`, `~됑`, `~~~`, `!`처럼 장난스럽게 변형한 어미와 기호는 원문이나 최근 피드백이 충분히 친근한 분위기일 때만 드물게 사용한다. 모든 답장에 억지로 넣거나 진지한 지적에 사용하지 않는다.
- 문장은 카카오톡으로 설명하듯 자연스럽게 이어 쓸 수 있지만, 서로 다른 수정 요청이 섞일 때는 줄바꿈이나 목록으로 나눠 읽기 어렵지 않게 한다.

### 답장과 기록의 구분

- `학생에게 보낼 답장 작성` 요청이면 피드백 파일을 수정하지 않고 답장 문장만 작성한다.
- `기록해줘`, `파일에 반영해줘`, `피드백 내역에 추가해줘`라는 요청이 함께 있을 때만 해당 학생의 파일도 수정한다.
- 답장 작성과 기록을 모두 요청하면 먼저 바로 보낼 답장을 제시하고, 이후 날짜별 기록 규칙에 따라 파일을 갱신한다.
- 대상 학생이나 문맥이 불명확해도 문장 작성에 지장이 없다면 사용자가 준 표현을 기준으로 작성하고 불필요한 질문을 하지 않는다.

### 학생 질문 답변 파일 작성

사용자가 학생 질문에 대한 답변을 파일로 작성해 달라고 요청하면 지정된 파일명과 위치를 그대로 사용하고 다음 순서로 작성한다.

- 사용자가 경로 없이 `answer.md` 또는 `answer 파일`이라고만 지정하면 이 작업공간의 공용 답변 파일인 루트 `UIUX/work/answer.md`에 이어서 작성한다.
- 사용자가 `답변 작성해`라고 요청하면 학생 질문 답변 파일 작성 트리거로 처리한다. 별도 파일명이나 경로가 없으면 공용 `UIUX/work/answer.md`에 작성한다.
- 학생 폴더 안에 작성하라는 명시적인 요청이 있을 때만 `[학생이름]/answer.md`를 사용한다.
- 기존 공용 `answer.md`의 내용을 보존하고 새 답변은 문서 마지막에 `---` 구분선과 함께 추가한다.

```markdown
# 학생 질문 답변

## 학생 이름

## 질문

## 답변

## 참고한 내용
```

- `학생 이름`에는 질문한 학생의 이름을 기록한다.
- `질문`에는 학생의 핵심 혼동과 요청을 원래 의미가 바뀌지 않도록 정리한다.
- `답변`에는 강사가 학생에게 바로 보낼 수 있는 문장을 강사의 말투로 작성한다.
- `참고한 내용`에는 답변 판단에 사용한 이전 대화, 날짜별 지도 내용, 학생별 피드백 파일 또는 `Wireframe.md`의 관련 기준을 간략히 기록한다.
- 참고한 발언이 있으면 핵심 표현과 의미를 구분해서 적고, 대화에 없는 근거를 만들지 않는다.
- 여러 근거를 종합해 해석한 경우 마지막에 어떤 결론으로 답변했는지 한 문장으로 명시한다.
- 참고 링크가 판단 근거라면 링크와 링크에 관련된 피드백을 함께 기록한다.
- 답변 문장에는 불필요한 출처 설명을 섞지 않고, 근거는 `참고한 내용`에서 별도로 관리한다.
- 분석·피드백·단계 진행 답변은 학생이 판단 이유를 이해할 수 있는 연결된 설명문을 중심으로 작성한다.
- 표, 도식, 목록과 체크리스트는 설명을 대신할 수 없으며 설명문 뒤에서 내용을 요약하거나 확인하는 용도로만 사용한다.
- 각 주요 판단은 `현재 파일에서 확인한 내용 → 잘되었거나 부족한 이유 → 사용자에게 미치는 영향 → 유지하거나 수정할 방법`이 연결되도록 설명한다.
- 작업 항목만 나열하지 않고 왜 해당 작업을 먼저 해야 하는지와 수정 후 무엇이 달라지는지 함께 설명한다.
- 사용자가 특정 파일의 기존 내용은 유지하고 항목만 추가하라고 하면 다른 부분은 수정하지 않는다.
- 학생에게 전달하는 `답변` 본문에는 `**내용**` 형식의 굵은 글씨 표시를 사용하지 않는다. 강조가 필요하면 별도 기호를 붙이지 말고 문장 순서와 쉬운 표현으로 중요도를 전달한다.
- 학생에게 전달하는 `답변` 본문의 문장과 목록 끝에는 마침표 `.`를 붙이지 않는다. URL, 파일 확장자와 소수점처럼 내용 자체에 포함되는 마침표는 예외로 한다.
- 위 규칙은 공용 `answer.md`의 문서 구조를 위한 제목과 구분선에는 적용하지 않으며, 실제로 학생에게 복사해 보내는 `## 답변` 내용에 적용한다.

### 통합 지식베이스 갱신

- 학생별 피드백 파일에 새로운 날짜 기록이나 핵심 총요약이 추가되면 루트 `Wireframe.md`의 해당 학생 상태도 갱신한다.
- 반복되는 새로운 피드백 유형이 확인되면 `Wireframe.md`의 상황별 기준에 추가한다.
- 단순 문구 수정이나 중복 내용은 통합 문서에 추가하지 않는다.
- 학생별 피드백 파일에 진행 상태, 제출물, 강사 평가, 핵심 지도 방향, 다음 확인 사항 또는 참고 링크가 새로 추가되거나 변경되면 `Wireframe.md` 갱신을 선택 작업으로 두지 않고 같은 작업 안에서 반드시 함께 수행한다.
- 학생별 피드백 파일만 수정한 상태에서는 작업을 완료한 것으로 보고하지 않는다. `Wireframe.md`의 해당 학생 항목까지 동기화하고 검증한 뒤 완료를 보고한다.
- `Wireframe.md`에는 학생별 피드백의 전체 문장을 복사하지 않고, 최신 산출물과 현재 단계, 핵심 지도 방향, 다음 우선 확인 사항, 참고 링크를 검색 가능한 요약으로 반영한다.
- `Wireframe.md`의 기존 학생 항목에 문장이 잘못 합쳐졌거나 최신 기록과 충돌하는 내용이 있으면 해당 학생 항목 안에서 바로잡고, 다른 학생 항목은 수정하지 않는다.
- 사용자가 특정 파일만 수정하고 `Wireframe.md`는 변경하지 말라고 명시한 경우에만 동기화를 생략하며, 완료 보고에 동기화를 생략한 이유를 명시한다.

### 통합 지식베이스 동기화 절차

1. 학생별 `피드백[학생이름].md`의 수정 사항을 확정한다.
2. 같은 작업에서 `Wireframe.md`의 해당 학생 항목을 찾는다.
3. 최신 산출물, 현재 진행 단계, 강사 평가, 핵심 지도 방향, 다음 확인 사항과 참고 링크를 대조한다.
4. 새 정보와 변경된 정보만 `Wireframe.md`에 반영하고 다른 학생 내용은 건드리지 않는다.
5. 두 파일에서 학생 이름, 파일명, 상품 수, 단계, URL과 다음 행동이 서로 일치하는지 검색하여 확인한다.
6. 동기화 확인이 끝난 뒤에만 사용자에게 완료를 보고한다.

### 1. 학생과 날짜 식별

1. 사용자 메시지에서 학생 이름과 대화 날짜를 추출한다.
2. `2026년 8월 13일 목요일` 같은 표현은 `2026-08-13`으로 정규화한다.
3. 여러 날짜가 포함되면 날짜별로 분리한다.
4. 날짜를 알 수 없으면 임의로 추정하지 말고 `날짜 미상`으로 기록한다.

### 2. 발화자 역할 구분

- 강사 발화: 지시, 평가, 참고 자료, 수정 방향, 다음 과제
- 학생 발화: 질문, 작업 의도, 이해 내용, 어려움, 동의 또는 오해
- 카카오톡의 `사진저장하기`, `링크 스크랩 이미지`, 시간 표시 등 시스템 문구는 핵심 기록에서 제외한다.
- 학생이 이해했다고 답한 경우에도 실제 반영 완료로 간주하지 않는다. `이해 확인`, `반영 여부는 다음 제출에서 점검`으로 기록한다.

### 3. 핵심 내용 추출

대화에서 다음 정보를 우선 추출한다.

- 피드백이 발생한 배경과 현재 작업 상태
- 강사가 유지하라고 한 내용
- 강사가 추가·수정·삭제하라고 한 내용
- 학생이 질문하거나 혼동한 지점
- 학생이 스스로 정리한 방향
- 다음 제출에서 확인할 구체적인 항목
- 참고 링크와 참고 목적

대화에 없는 평가, 점수, 학생의 감정이나 의도를 임의로 만들지 않는다.

### 3-1. 참고 링크 정리

대화에 URL이 포함되면 해당 날짜 기록에 `#### 사용한 참고 링크`를 만들고, 링크와 링크에 관련된 피드백만 간략하게 함께 적는다.

```markdown
- [사이트명 또는 확인된 페이지 제목](URL) — 이 링크와 관련해 전달된 핵심 피드백을 한 문장으로 요약합니다.
```

- URL 원문을 누락하거나 임의로 단축하지 않는다.
- 페이지 제목을 확인할 수 있으면 제목을 링크 레이블로 사용한다.
- 제목을 확인하지 못하면 `사이트명 + 참고 링크 번호`처럼 간단하고 중립적인 이름을 사용한다.
- 링크 앞뒤의 대화 문맥을 근거로 해당 링크와 직접 관련된 피드백만 한 문장으로 요약한다.
- 링크 목적이 불명확하면 `관련 피드백 목적 확인 필요`라고 기록한다.
- 접근할 수 없는 링크의 페이지 내용이나 디자인을 추측하지 않는다.
- 같은 링크가 여러 날짜에 다시 사용되면 해당 날짜의 새로운 사용 목적이 있을 때만 다시 기록한다.
- 링크 기록을 위해 다른 피드백 내용을 수정하거나 불필요한 분석 표를 추가하지 않는다.

### 4. 기존 기록과 병합

1. 대상 피드백 파일을 먼저 읽는다.
2. 새 기록은 해당 `####` 대제목 아래의 날짜 목록에서 오름차순에 맞는 `##### YYYY-MM-DD` 구간에 추가한다.
3. 같은 대제목과 날짜 기록이 있으면 기존 내용을 보존하고 새 정보만 해당 날짜 구간에 병합한다.
4. 같은 대화가 이미 기록되어 있으면 중복 문장을 추가하지 않는다.
5. 과거 피드백과 새 피드백이 충돌하면 과거 내용을 삭제하지 말고, 새 날짜에 `방향 변경` 또는 `추가 지침`으로 명시한다.
6. 원본 학생 제출 파일은 사용자가 요청하지 않는 한 수정하지 않는다.

### 5. 실행 가능한 기록으로 변환

추상적 표현은 대화의 의미를 바꾸지 않는 범위에서 확인 가능한 작업으로 변환한다.

- `브랜드를 돋보이게` → 브랜드 서사, 대표 메시지, 이미지 비중과 강조 섹션 확인
- `다양한 레이아웃` → 분할, 교차, 대형 이미지, 에디토리얼 구성 등 반복 카드 외 구조 확인
- `회사 자랑 추가` → 철학, 기술력, 성과, 제작 과정과 검증 가능한 근거 확인

`#### 다음 확인 사항` 아래의 각 날짜 기록은 체크박스로 작성한다.

작업 수정 지침은 강사의 발언과 학생의 과제 범위 안에서만 작성한다. 대화에 없는 화면 순서, 섹션 구성 또는 `권장 화면 흐름`을 새로 제안하지 않는다.

### 6. 누적 총요약 갱신

`## 누적 총요약`은 항상 문서의 마지막 섹션이어야 한다. 새 기록을 추가할 때마다 전체 날짜 기록을 바탕으로 다시 작성한다.

총요약에는 다음을 포함한다.

1. 학생의 현재 프로젝트와 진행 단계
2. 반복적으로 확인되는 강점
3. 반복되는 문제나 혼동
4. 지금까지의 핵심 지도 방향
5. 학생이 이해했으나 아직 결과물로 확인되지 않은 사항
6. 다음 피드백 때 가장 먼저 확인할 3~5개 항목

최근 피드백을 반영하되 과거의 중요한 맥락을 잃지 않는다. 날짜별 세부 내용을 그대로 반복하지 말고 강사가 다음 상담 전에 빠르게 읽을 수 있는 분량으로 종합한다.

## 제출물 검토 규칙

- 사용자가 제출물 검토도 요청한 경우 실제 파일을 확인하고 근거가 있는 내용만 기록한다.
- 파일명, 문서 구조, 화면 수, 접근성 요소 등 확인 가능한 사실과 개선 의견을 구분한다.
- 참고 링크가 있으면 가능한 범위에서 확인하되, 접근할 수 없는 링크의 내용을 추측하지 않는다.
- 외부 사례는 모방 지시가 아니라 어떤 특성을 참고하는지 기록한다.
- 제출 파일이 없으면 `제출물 확인 불가`라고 기록하고 필요한 제출 항목을 남긴다.

## 작성 원칙

### 강사 원문과 카카오톡 대화 기록 구분

학생 피드백 파일을 작성할 때 입력 자료의 유형에 따라 다음 규칙을 구분하여 적용한다.

#### 1. 강사가 직접 작성한 피드백 원문

- 사용자가 학생에게 전달할 목적으로 직접 작성한 피드백 문장을 제공하고 이를 기록해 달라고 요청하면 `#### 강사 피드백`의 해당 날짜에 원문 그대로 기록한다.
- 맞춤법, 띄어쓰기, 말투, 이모티콘, 문장 순서, 번호와 줄바꿈을 임의로 수정하지 않는다.
- 원문을 요약하거나 명사형 목록으로 변환하지 않는다.
- 표준 구조를 위한 `#### 강사 피드백`과 `##### YYYY-MM-DD` 제목만 추가할 수 있다.
- 실행 항목은 `작업 수정 지침`, `다음 확인 사항`과 `누적 총요약`에 별도로 정리할 수 있지만, 정리한 내용으로 강사 원문을 대체하거나 원문의 일부를 삭제하지 않는다.
- 이 원문 보존 규칙은 아래의 `와이어프레임 단계별 강사 피드백 작성 규칙`보다 우선한다. 사용자가 직접 작성한 원문에는 단계 제목이나 명사형 표현을 임의로 추가하지 않는다.

#### 2. 카카오톡 대화 내용

- 사용자가 학생과 나눈 카카오톡 대화 전체 또는 대화 캡처의 내용을 보내면 기존 입력 처리 파이프라인에 따라 정리하여 기록한다.
- 카카오톡 대화는 원문 전체를 그대로 복사하지 않고 강사 발화와 학생 발화를 구분하여 핵심 내용을 추출한다.
- 강사의 지시, 평가, 수정 방향과 다음 과제는 `강사 피드백` 또는 `작업 수정 지침`에 정리한다.
- 학생의 질문, 작업 의도, 이해 내용, 어려움과 반응은 `학생의 질문·반응 및 이해도`에 정리한다.
- 대화에 포함된 작업 상태와 제출 배경은 `피드백 배경`에 정리한다.
- URL은 `사용한 참고 링크`, 제출물과 검토 결과는 `제출물 검토 메모`에 기록한다.
- 다음 제출에서 확인할 내용은 실행 가능한 체크박스로 `다음 확인 사항`에 작성한다.
- 카카오톡의 시간 표시, `사진 저장하기`, 링크 미리보기와 같은 시스템 문구는 기록에서 제외한다.
- 대화의 의미와 강사의 지도 방향은 유지하되 중복 표현과 구어체는 기록용 문장으로 간결하게 정리한다.
- 대화에 없는 평가, 학생의 의도, 새로운 과제나 화면 구성을 임의로 추가하지 않는다.

#### 3. 입력 유형 판단

- 사용자가 “이 내용 그대로 기록해줘”, “원문으로 넣어줘”라고 요청하면 강사 원문 보존 규칙을 적용한다.
- 사용자가 “카톡 대화 기록해줘”, “대화 내용 정리해줘”라고 요청하거나 강사와 학생의 대화가 함께 제공되면 카카오톡 대화 정리 규칙을 적용한다.
- 강사 원문과 카카오톡 대화가 함께 제공되면 강사가 직접 작성한 피드백 문장만 원문으로 보존하고, 나머지 대화는 기존 방식으로 정리한다.
- 입력 유형이 불분명하지만 강사와 학생의 발화가 구분되는 대화 형식이면 카카오톡 대화로 판단하여 정리한다.

- 강사가 나중에 바로 기억할 수 있도록 구체적이고 간결하게 작성한다.
- 학생에게 전달 가능한 존중하는 표현을 사용한다.
- 사실, 강사의 지시, 학생의 발언, AI가 정리한 실행 항목을 혼동하지 않는다.
- 기존 기록을 임의로 삭제하거나 덮어쓰지 않는다.
- 사용자가 특정 부분만 수정하라고 한 경우 그 부분 외의 내용은 변경하지 않는다.
- 민감한 개인정보와 대화에 불필요한 연락처는 기록하지 않는다.
- 각 `####` 대제목 아래에 날짜별 기록을 작성하고 총요약을 마지막에 갱신한다.

### 와이어프레임 단계별 강사 피드백 작성 규칙

- `#### 강사 피드백`의 `##### YYYY-MM-DD` 구간 아래에서 와이어프레임 작업은 `###### 와이어프레임 1단계`부터 `###### 와이어프레임 4단계`까지 학생이 진행할 순서에 따라 각각 구분하여 작성한다.
- 와이어프레임 1단계는 `초반에 생성한 와이어프레임 기반으로 초안 생성`으로 작성한다.
- 와이어프레임 2단계는 `최소 15개 상품이 배치되도록 설계`로 작성한다.
- 와이어프레임 3단계는 `브랜드 정보와 최소 15개 상품 배치가 각 섹션에 조화롭게 배치될 수 있도록 수정`으로 작성한다.
- 와이어프레임 4단계는 `3단계에서 진행한 와이어프레임을 기반으로 아래 내용 진행`을 먼저 작성한 뒤 해당 단계의 세부 피드백을 목록으로 구분한다.
- 단계별 강사 피드백은 `~합니다`, `~습니다` 형태를 사용하지 않고 `생성`, `설계`, `수정`, `추가`, `보강`, `분석`, `반영`과 같은 간결한 목록형 문장으로 작성한다.
- 각 항목은 `~진행`, `~수정`, `~생성`, `~추가`, `~분석`, `~전달`처럼 실행할 작업이 드러나는 명사형 표현으로 끝내며 문장 끝에 마침표를 붙이지 않는다.
- 기존 피드백을 단계별로 나눌 때 원래 내용과 항목 순서는 유지하고, 단계 제목과 구분에 필요한 문구만 추가한다.
- 사용자가 특정 학생 또는 `#### 강사 피드백` 구간만 수정하도록 지정하면 해당 학생의 해당 구간만 수정하며 다른 학생 파일과 다른 구간은 절대 수정하지 않는다.

### 와이어프레임 4단계 답변 작성 규칙

#### 기본 원칙

- 현재 작업과 가까운 기존 학생의 와이어프레임 4단계 피드백이 있으면 선별해 참고한다.
- 기존 학생 피드백에서는 진행 방법과 판단 기준만 참고하고 다른 학생의 브랜드명, 문장, 상품, 화면 구성을 복사하지 않는다.
- 해당 학생의 최신 와이어프레임, 이전 단계 피드백, 브랜드 정보, 기존 분석 파일을 근거로 학생 브랜드에 맞게 새로 작성한다.
- 기존 내용을 삭제하거나 결과 전체를 교체하기보다 현재 강점을 유지하고 필요한 요구와 콘텐츠를 추가하는 방향을 우선한다.
- 구체성은 실제 파일에서 확인한 구간과 콘텐츠를 근거로 확보하고 학생에게 없는 상품, 기능, 화면을 임의로 만들어 채우지 않는다.

#### 설명 우선 작성

- 4단계 답변은 `현재 결과에 대한 설명 → 설계 문제와 이유 → 디자인 문제와 이유 → 보완 클라이언트 선정 이유 → 레퍼런스 적용 이유 → 병합 판단 이유 → 실행 목록과 완료 기준` 순서로 작성한다.
- 현재 결과 분석, 설계 관점, 디자인 관점, 보완 클라이언트, 레퍼런스와 병합 기준에는 각각 학생이 이해할 수 있는 설명문을 먼저 작성한다.
- `유지`, `수정`, `적용`, `제외` 같은 결론만 제시하지 않고 왜 그렇게 판단했는지 실제 화면 구간과 연결해 설명한다.
- 보완 클라이언트는 역할과 요구사항만 나열하지 않고 현재 부족점을 해결하는 데 왜 필요한 역할인지 설명한다.
- 레퍼런스는 특징 목록만 작성하지 않고 현재 결과의 어떤 문제를 어떤 원리로 보완할 수 있는지 설명한다.
- 병합 기준은 가져올 항목을 나열하기 전에 기존 결과를 유지해야 하는 이유와 새 결과를 선택적으로 적용해야 하는 이유를 설명한다.
- 표, 요청문, 진행 순서와 체크리스트는 설명이 끝난 뒤 실행과 검수에 사용하는 보조 자료로 배치한다.

#### 현재 결과 분석

- 먼저 3단계 요구의 반영 상태, 현재 완성도와 4단계에서도 유지할 강점을 판단한다.
- 부족한 부분은 `설계 관점`과 `디자인 관점`으로 구분하여 분석한다.
- 설계 관점에서는 정보 우선순위, 콘텐츠 연결, 구간별 목적, 대표 콘텐츠와 전체 콘텐츠의 역할, 반복과 충돌, 정보 일관성을 확인한다.
- 디자인 관점에서는 브랜드 인상, 시각적 위계, 화면 리듬, 반복 구성, 여백, 정보 밀도와 해당 브랜드의 공통 시각 언어를 확인한다.
- 추상적인 평가로 끝내지 않고 현재 어느 구간에 어떤 문제가 있으며 무엇을 유지하고 어떻게 보완할지 연결한다.
- 상품이나 반복 콘텐츠가 있는 경우 구간별 이름, 분류, 가격과 설명이 같은 기준으로 유지되는지 확인한다.

#### 보완 클라이언트

- 현재 분석에서 발견한 부족한 부분을 직접 해결하는 보완 클라이언트를 추가한다.
- 보완 클라이언트는 기존 클라이언트와 같은 요구를 반복하거나 새로운 기능과 상품을 무조건 늘리는 역할로 만들지 않는다.
- 역할, 현재 문제, 목표, 유지 요구, 설계 요구, 디자인 요구와 완료 기준을 중심으로 작성한다.
- 답변에 필요하지 않은 이름, 나이, 생활 환경과 개인 설정은 임의로 만들지 않는다.
- 학생이 작업에 바로 사용할 수 있도록 해당 브랜드와 현재 결과에 맞춘 보완 클라이언트 요청문을 함께 제공한다.

#### 레퍼런스 탐색과 분류

- 레퍼런스를 방대하게 새로 수집하지 않고 학생이 선택한 사이트 형식과 기존 리서치 목록에 가까운 사례를 우선한다.
- 레퍼런스는 `사용성`, `심미성`, `무드`로 구분하고 각 분류에서 현재 부족점을 보완하는 데 필요한 최소 사례만 선정한다.
- 일반적으로 분류별 대표 사례 1개를 우선하며 비교가 필요한 경우에만 보조 후보를 추가한다.
- `분류`에는 레퍼런스 이름, 확인한 주소, 사용성·심미성·무드 중 하나, 선택 이유와 보완할 현재 구간을 작성한다.
- `분석`에는 확인한 페이지와 구간, 잘된 점, 현재 결과의 부족한 점, 유지할 내용, 참고할 원리, 적용 구간, 보완 방법, 복제하지 않을 요소와 병합 우선순위를 작성한다.
- `예쁘다`, `좋다`와 같은 감상으로 끝내지 않고 `현재 문제 → 참고 원리 → 적용 위치 → 기대되는 보완`의 관계가 드러나게 작성한다.
- 레퍼런스의 특징을 사실처럼 설명할 때는 실제 페이지나 기존 분석 근거를 확인하고 확인하지 않은 사례는 확정 레퍼런스가 아니라 후보로 표시한다.

#### 기존 분석 파일 보존

- 기존 분석 파일의 내용을 수정하거나 삭제하지 않는다.
- 파일 아래에 와이어프레임 4단계 레퍼런스 탐색 기준, 분류 결과와 분석 내용을 추가하도록 안내한다.
- 새 분석은 현재 와이어프레임의 구체적인 부족점과 실제 적용할 구간이 연결되도록 작성한다.

#### 기존 결과와 새 결과의 최종 병합

- 답변에서 `기존 결과에서 유지할 내용`, `새 클라이언트 결과에서 가져올 내용`, `새 결과에서 가져오지 않을 내용`을 구분한다.

- 기존 콘텐츠 기준과 충돌하는 새 상품, 기능, 설명은 기존 기준에 맞추거나 제외한다.
- 레퍼런스의 문장과 디자인을 그대로 복제하지 않고 해당 학생의 브랜드 언어와 기존 콘텐츠에 맞게 변환한다.
- 마지막에는 실제 와이어프레임 구간별 보완 목표, 진행 순서와 4단계 완료 확인 기준을 제공한다.
