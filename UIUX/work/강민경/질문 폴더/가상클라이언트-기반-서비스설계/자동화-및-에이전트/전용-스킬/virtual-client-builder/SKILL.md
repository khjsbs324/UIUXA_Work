# Virtual Client Builder

## 목적

승인된 종합 분석을 실제 가상 클라이언트 문서로 변환한다. 사용자 문제와 요구를 의뢰자의 프로젝트 목적과 요구사항으로 바꾸되, 원본 근거·불확실성·사용자 유형 간 차이를 보존한다.

## 필수 입력 확인

1. 승인 상태가 `USER_APPROVED` 또는 동등한 명시적 승인인지 확인한다.
2. 전체 종합 분석과 가상 클라이언트 입력 패키지를 모두 읽는다.
3. 기존 `INT-*`, `PER-*`, `PDF-*`, `VCR-*`, `CONFLICT-*`, `MISSING-*` ID를 변경하지 않는다.
4. 기존 `VC-*` ID가 있으면 충돌 방지를 위해 새 생성물에는 `VCG-*`를 사용한다.
5. 근거가 약하거나 검증이 필요한 항목은 승인 클라이언트의 사실로 승격하지 않는다.

입력이 승인되지 않았거나 핵심 근거 파일이 없으면 생성을 중단하고 누락 사항을 보고한다.

## 생성 흐름

### 1. 사용자 유형과 이용 모드 분리

- 핵심 문제, 목표, 행동, 이용 매체, 기록 밀도, 선택 기준을 비교한다.
- 한 사람이 여러 이용 모드를 보인다면 곧바로 서로 다른 사람으로 가정하지 않는다.
- 핵심 문제와 목표가 의미 있게 다를 때만 별도 클라이언트 후보로 만든다.
- 80% 이상 유사하면 통합 후보로 표시한다.

### 2. 의뢰자 관점으로 변환

다음 연결을 유지한다.

`사용자 상황 → 사용자 문제 → 사용자 목표 → 사용자 요구 → 의뢰 목적 → 클라이언트 요구`

가상 클라이언트는 사용자의 복사본이 아니라, 해당 사용자 문제를 해결하려는 프로젝트 의뢰자다. 실제 인명이나 회사가 근거에 없으면 역할 중심 식별명을 사용하고 `생성 식별명`임을 표시한다.

### 3. 상태 판정

- `APPROVED_VIRTUAL_CLIENT`: 강한 원본 또는 교차 근거가 있고 다른 유형과 명확히 구분된다.
- `CANDIDATE`: 실제 근거는 있으나 독립 유형인지 추가 검증이 필요하다.
- `HOLD`: 설정·가설 비중이 크거나 핵심 행동 근거가 부족하다.
- `REJECTED`: 근거가 없거나 다른 클라이언트와 실질적으로 동일하다.

### 4. 요구사항 생성

승인 입력의 요구 후보를 클라이언트별로 배정한다. 각 요구에는 다음을 기록한다.

- 요구 ID: `VCG-001-REQ-001` 형식
- 요구 유형과 내용
- 해결할 문제와 관련 목표
- 명시적·잠재적 구분
- 중요도: 필수 / 높음 / 중간 / 낮음 / 확인 필요
- 브랜드 적합성
- 원본 근거 ID와 상위 `VCR-*` ID
- 검증 필요 여부

근거가 같은 요구를 표현만 바꾸어 늘리지 않는다. 확인 필요 요구는 `필수`로 지정하지 않는다.

요구 수준 상태는 Client 상태와 분리하여 다음처럼 사용한다.

- `승인`: 현재 근거로 사용할 수 있는 요구. 단, 잠재 요구나 설계 원칙이면 그 근거 성격을 함께 표시한다.
- `조건부 승인`: 요구 방향은 유효하지만 적용 조건이 남아 있다. 해제 조건과 관련 `MISSING-*`, `CONFLICT-*`를 기록하고 일반 승인 수에 합산하지 않는다.
- `후보`: 실제 근거는 있으나 Client 독립성 또는 요구 적용 범위 검증이 필요하다.
- `HOLD`: 근거·운영 조건이 부족해 확정하거나 구현 범위로 전달할 수 없다.

공통 원칙 참조를 각 Client의 직접 행동 사실로 바꾸지 않는다. 조건부 설계 원칙은 확정 사용자 사실과 구분한다.

### 5. 고정 조건과 설계 가능 범위 분리

클라이언트별로 다음을 구분한다.

- 고정 조건: 핵심 사용자, 해결할 문제, 의뢰 목적, 승인 요구, 금지·제한 조건
- 설계 가능 범위: 정보 우선순위, 표현 방식, 세부 흐름 후보

페이지, 메뉴, UI 구성요소, 와이어프레임은 확정하지 않는다.

### 6. 공통 원칙과 충돌 보존

- 여러 클라이언트에 반복되는 요구는 공통 원칙으로 별도 관리한다.
- 상반된 요구를 삭제하지 말고 관련 클라이언트와 원인을 연결한다.
- 자료에 없는 성공 수치나 KPI를 만들지 않는다. 성공 기준은 근거가 있는 정성 조건으로 작성한다.

## 클라이언트 문서 구조

각 클라이언트에 최소한 다음을 포함한다.

1. ID, 생성 식별명, 상태, 우선순위, 근거 강도
2. 역할과 대표 사용자 유형
3. 배경과 해결하려는 문제
4. 한 문장 프로젝트 의뢰 목적
5. 주요 사용자 상황·행동·목표
6. 핵심 요구와 상세 요구사항
7. 고정 조건과 설계 가능 범위
8. 정성적 성공 기준
9. 제약·충돌·추가 확인 질문
10. 원본 추적 정보

## 품질 검증

- 모든 승인 클라이언트가 강한 근거를 갖는지 확인한다.
- 클라이언트 간 핵심 문제·목표·행동이 의미 있게 다른지 확인한다.
- 생성 식별명과 분석 사실을 구분한다.
- 명시적 요구와 잠재 요구를 구분한다.
- 약한 페르소나 설정을 실제 행동 사실로 바꾸지 않는다.
- 이전 단계 예시 브랜드의 기능·색상·CTA를 복사하지 않는다.
- 사이트 분석, 메뉴·콘텐츠·기능의 최종 확정, 화면 설계를 실행하지 않는다.
- 검토 결과가 `APPROVED`가 아니면 최종 승인 세트로 표시하지 않는다.

## 종료

가상 클라이언트, 요구사항, 공통 원칙, 추적성, 검토 보고서를 저장한 뒤 상태를 `USER_APPROVAL_PENDING`으로 설정한다. 사용자 승인 전 사이트 경험 분석이나 다음 설계 단계로 이동하지 않는다.
