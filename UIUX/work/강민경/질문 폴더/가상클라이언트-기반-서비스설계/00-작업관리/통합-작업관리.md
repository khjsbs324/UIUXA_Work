# 브랜드 UX 단계별 제작 통합 작업관리

이 문서 하나로 현재 상태, 실행 순서, 단계별 출력 기준, 검증, 버전 관리와 병합 차단 조건을 관리한다. 운영 문서나 Skill은 실제 도출 결과를 대신할 수 없다. 실제로 도출한 값은 이 루트의 `<번호>-<단계명>-출력물/`에 저장한다.

## 1. 현재 상태

- 현재 단계: `03-제품콘텐츠`
- 현재 버전: `V2`
- 활성 결과: `../03-제품콘텐츠-출력물/제품콘텐츠-도출결과-V1.md`
- Client 생성 수: 51명 (개별 상세 파일 51개 + 인덱스 1개)
- 요구사항 도출 수: 51건
- 완료 범위: 기존 39명 정규화, 추가 12명 생성, Client 필수 필드 51/51, 요구사항 중복·충돌 검토 완료

- Client 출력 원칙: Client는 병합하지 않으며 `01-클라이언트생성-출력물`에 Client 1명당 상세 결과 파일 1개를 둔다. `00-클라이언트생성-인덱스-V2.md`는 목록·판정·검증만 관리한다.
- 남은 검증: 요구사항 V2 결과 확인 완료
- 다음 단계: 제품군 분류 및 약 200개 제품 후보 생성
- 최종 병합: 금지

## 2. 파일과 버전 관리

### 활성 결과 구조

```text
가상클라이언트-기반-서비스설계/
├─ 01-클라이언트생성-출력물/
│  ├─ 00-클라이언트생성-인덱스-V2.md
│  └─ VC-01~VC-51 개별 상세 파일
├─ 02-요구사항분석-출력물/
└─ 03-제품콘텐츠-출력물/
```

- 각 `<번호>-<단계명>-출력물/`에는 해당 단계의 실제 도출 결과만 저장한다.
- 각 단계 폴더는 `<번호>-<단계명>-출력물` 형식으로 이름을 붙인다.
- 예정 단계명은 `01-클라이언트생성-출력물`, `02-요구사항분석-출력물`, `03-제품콘텐츠-출력물`, `04-사이트구조맵-출력물`, `05-서비스흐름도-출력물`, `06-화면설계서-출력물`, `07-스토리보드-출력물`, `08-전체연결검증-출력물`, `09-병합결과-출력물`, `10-와이어프레임-출력물`, `11-스타일가이드-출력물`, `12-Figma-출력물`, `13-최종제출-출력물`이다.
- 예정 단계 폴더는 해당 단계가 시작될 때만 만든다.
- `00-작업관리/`에는 통합 작업관리 MD와 상태 문서만 저장한다.
- `전용-스킬/`에는 자동 실행에 필요한 `SKILL.md`와 인터페이스 파일만 저장한다.
- `보관/`에는 기존 통합 결과와 압축된 이전 작업을 보존하며 활성 결과로 계산하지 않는다.
- 작업상태, 체크리스트, 감사, 실행 프롬프트, README를 단계별 출력 폴더에 넣지 않는다.
- 단계가 실제로 시작될 때만 해당 단계 폴더를 만든다. 빈 폴더를 미리 만들지 않는다.
- 같은 단계의 신규 생성, 추가 탐색, 재검수, 수정은 별도 폴더를 만들지 않는다.
- 최초 도출은 `V1`, 실질적인 추가·수정 후 재검증 결과는 같은 폴더의 `V2`, `V3`로 관리한다.
- 생성·구분·탐색·검증·판정은 해당 버전 문서 안의 Section으로 기록한다.
- 후보 하나마다 MD를 만들지 않는다. 단, Client 단계는 사용자 요구에 따라 Client 1명당 개별 상세 MD를 유지하고 인덱스는 목록·집계만 관리한다.
- 사이트맵·흐름도·화면설계·스토리보드의 시각 비교가 필요할 때만 같은 버전명의 HTML을 추가한다.
- 운영 규칙, 체크리스트, 실행 프롬프트를 결과 폴더에 넣지 않는다.
- 과거 배치·회차·반려 병합본은 `보관/이전작업-V1.zip` 안에서만 보존하며 활성 결과로 계산하지 않는다.
- 최신 파일은 파일명에서 가장 높은 `Vn`으로 판별한다. `최종`, `완료`라는 표현은 단계 게이트 통과 전 사용하지 않는다.

### 출력물 파일명 판별

- `도출결과-Vn`: 현재 단계에서 생성·분류·탐색·검증한 실제 후보 결과다.
- `병합결과-Vn`: 모든 후보 검증 후 사용자가 병합을 승인했을 때만 생성한다.
- `최종제출-Vn`: 와이어프레임·스타일·Figma까지 완료하고 제출용으로 확정한 파일에만 사용한다.
- 같은 단계에서 가장 높은 `Vn` 파일 하나를 현재 결과로 판별한다.
- 검증 보고서, 수정 보고서, 신규 목록을 별도 파일로 만들지 않고 해당 `도출결과-Vn` 안의 Section으로 기록한다.
- 파일명과 문서 첫머리에 단계, 버전, 상태, 도출 수와 다음 작업을 표시한다.

## 3. 전체 진행 순서

1. 가상 클라이언트 대량 생성·정규화
2. 클라이언트 중복·충돌·공백 검증
3. 요구사항과 제품·콘텐츠 후보 도출
4. 사이트맵 복수안 생성·검증
5. 서비스 흐름도 복수안 생성·검증
6. 화면설계서 복수안 생성·검증
7. 메인·카테고리·브랜드 소개 스토리보드 복수안 생성·검증
8. 전 단계 연결성과 누락 검증
9. 사용자에게 `이제 병합 진행을 추천합니다`라고 먼저 보고
10. 사용자 승인 후에만 단계별 병합본 제작
11. 와이어프레임, 스타일 가이드, Figma 제작

앞 단계가 검증되지 않으면 다음 단계로 넘어가지 않는다. 제품은 중요한 축이지만 브랜드, 사용자, 정보구조, 흐름, 화면, 스토리보드와 동등하게 다룬다.

## 4. 근거와 추적 체계

`SOURCE → FINDING → CLIENT → REQ → PRODUCT → PAGE → FLOW → SCREEN → STORYBOARD`

- 원자료 사실과 합성 가설을 구분한다.
- 실제 조사 참여자가 아닌 가상 인물은 합성 관점임을 표시한다.
- 확인되지 않은 가격, 재고, 배송, 소재, 성능, 브랜드 공식 의미를 사실처럼 쓰지 않는다.
- 각 단계는 상위 ID와 하위 사용처를 함께 기록한다.
- 연결되지 않은 항목은 삭제하지 않고 `HOLD`와 보류 이유를 기록한다.

## 5. 공통 반복 방식

각 버전에서 다음 순서를 한 번의 작업 단위로 실행한다.

1. 생성: 기존 집합과 다른 문제·행동·판단·실패 관점을 발산한다.
2. 구분: 목적, 과업, 페이지, 상태, 근거 수준으로 분류한다.
3. 탐색: 중복, 충돌, 누락, 예외, 브랜드 불일치를 찾는다.
4. 검증: 직관·창의·통합·근거 관점으로 독립 점검한다.
5. 수정: 오류와 공백을 해당 버전 안에서 보완한다.
6. 판정: `KEEP`, `MERGE`, `REVISE`, `HOLD`, `EXCLUDE`를 부여한다.
7. 버전 전환: 실질적인 내용 변경이 필요할 때만 다음 `Vn`을 만든다.

단순 문구 수정이나 파일명 정리는 새 버전 생성 사유가 아니다.

## 6. 단계별 실제 출력 기준

### 01 가상 클라이언트

각 Client에 다음을 포함한다.

- VC ID와 가상 이름
- 현재 판정과 근거 수준
- 상황, 목표, 핵심 과업, 행동 흐름
- 불편·문제, 판단 기준, 요구
- 성공 조건과 실패 조건
- 제품 요구 방향과 브랜드 접점
- 충돌 Client와 추적 ID

생성 수와 공식 채택 수를 모두 기록한다. 신규·재검수 결과를 별도 MD로 분리하지 않고 동일 버전 문서의 검증 Section에 기록한다.

### 02 요구사항·제품 후보

- Client별로 여러 제품 방향을 발산한다.
- 원시 제품 후보는 약 200개를 목표로 한다.
- 각 제품에 Product ID, Client·REQ 연결, 이름, 유형, 카테고리, 사용 상황, 해결 문제, 핵심 특징, 브랜드 적합성, 차별점, 사실 상태와 판정을 기록한다.
- 메인 대표 제품은 최소 15개이며, 약 200개 중 선정한 이유를 남긴다.
- 가상 제품은 실제 판매·구매 가능 제품으로 오인되지 않게 표시한다.

### 03 사이트맵

- 하나의 Client 요구에서 복수 구조 방향을 생성한다.
- Page ID, 목적, Parent, Depth, 상태, Client·REQ·Product 연결, 콘텐츠·기능, 교차 링크와 후보 계보를 기록한다.
- 여러 후보를 생성한 뒤 검증하며 이 단계에서 하나로 병합하지 않는다.

### 04 서비스 흐름도

- 우선 과업별 복수 흐름을 생성한다.
- 시작, Trigger, 단계, 분기, Empty, Error, Offline, 취소, 중단, Resume, 복귀, 종료와 관련 ID를 기록한다.
- 정상 흐름만 만들지 않고 실패·복귀 상태를 포함한다.

### 05 화면설계서

- 주요 Page와 상태별 복수 화면 접근을 생성한다.
- Screen ID, Page·Flow, 목표, 진입, Section, Content, UI, 행동, 상태, Validation, 반응형, 접근성, 다음 화면, Product와 근거를 기록한다.
- 조작 결과와 상태 변화가 흐름도와 일치해야 한다.

### 06 스토리보드

메인, 카테고리, 브랜드 소개를 각각 여러 안으로 생성한다. 각 안에 목적, 콘텐츠 우선순위, 실제 후보 카피, 레이아웃, 컴포넌트, 행동, 상태·예외, 반응형, 접근성, 브랜드 표현, 제품과 추적 ID를 포함한다.

#### 메인 페이지

- 일반 쇼핑몰 홈이 아니라 회사·브랜드 소개와 제품 탐색을 결합한 긴 스크롤 랜딩 페이지다.
- 브랜드 서사와 제품 섹션이 서로 분리되지 않고 자연스럽게 이어져야 한다.
- 최소 15개 대표 제품을 배치하고 가로 레일·슬라이드의 발견성, 수동 제어, 현재 위치와 전체 보기를 검증한다.

#### 카테고리 서브페이지

- 제품군을 의미 있는 기준으로 분류해 모아 보여준다.
- 상단에는 포트폴리오의 시각적 인상을 전달하는 Hero를 둔다.
- Hero가 카테고리 제목, 범위, 탐색 시작점을 가리지 않게 한다.
- 판매 전환보다 분류 이해, 비교와 탐색 사용성을 우선한다.

#### 브랜드 소개페이지

- 브랜드가 추구하는 방향, 특징, 차별점, 기록 철학과 제품 원칙을 설명한다.
- 한국적 정서는 장식이 아니라 태도, 재료, 여백과 사용 경험으로 연결한다.
- 브랜드 주장과 제품 특징이 직접 연결되어야 한다.

## 7. 검증과 차단 조건

- `Critical`: 근거 위조, 범위 밖 확정, 핵심 추적 단절. 즉시 중단한다.
- `High`: 필수 단계·필드·페이지 역할 누락. 다음 단계로 넘어가지 않는다.
- `Medium`: 중복, 병합 경계, 일부 상태·근거 보강 필요. 수정 후 재검증한다.
- `Low`: 표현·정렬·경미한 표기 문제. 같은 버전에서 정리한다.

단계 통과 조건:

- 필수 필드와 추적 ID가 모두 존재한다.
- 생성 수, 판정 수와 제외 이유가 계산된다.
- 페이지별 역할과 브랜드 원칙이 충돌하지 않는다.
- 실제 출력 파일에서 후보별 내용을 직접 확인할 수 있다.
- `Critical 0`, `High 0`이며 Medium의 처리 계획이 명시된다.

## 8. 최종 병합 차단

- 모든 단계의 후보 생성과 재검증이 끝나기 전에는 병합하지 않는다.
- 병합 준비도 점검도 기존 버전 문서 안에 기록하며 별도 `최종게이트` 폴더를 만들지 않는다.
- 준비가 완료되면 사용자에게 먼저 `이제 병합 진행을 추천합니다`라고 보고한다.
- 사용자 승인 후에만 사이트맵 1개, 흐름도 1개, 화면설계서 1개, 스토리보드 3개를 병합한다.
- 승인된 병합 파일은 `09-병합결과-출력물/`에 `*-병합결과-Vn` 형식으로 저장한다.
- 와이어프레임과 Figma는 승인된 병합 결과를 입력으로 사용한다.
- 전체 최종 제출 파일은 `13-최종제출-출력물/`에 `*-최종제출-Vn` 형식으로 저장한다.
