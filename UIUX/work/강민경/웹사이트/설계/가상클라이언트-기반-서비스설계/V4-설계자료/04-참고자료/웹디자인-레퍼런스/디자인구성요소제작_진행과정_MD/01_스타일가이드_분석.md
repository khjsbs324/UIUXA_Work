# AI ACE CBT Learning UI Kit 스타일 가이드 분석

> 분석 대상: `능력단위평가_디자인_구성요소_제작` 폴더의 스타일 가이드 1~13 JPG  
> 버전 표기: Community UI Kit · Version 1.0  
> 분석 단계: 기존 구조와 규칙 파악  
> 검수 상태: 스타일 가이드 JPG 13장 개별 재대조 완료
> 분석 원칙: 현 단계에서는 디자인 수정 및 선호 디자인 적용을 진행하지 않음

## 0. 분석 기준과 확인 범위

본 문서는 제공된 1차 분석을 참고하되, 스타일 가이드 원본 이미지 13장을 다시 대조하여 확정 정보, 시각적 추론, 확인 불가 정보를 구분한 재분석 결과다.

### 근거 수준

| 구분 | 의미 |
|---|---|
| **확정** | 원본 JPG에 문구, 수치, 토큰명 또는 예시가 직접 표시됨 |
| **시각 확인** | 예시의 형태와 색상 차이는 보이지만 속성명이 표시되지 않음 |
| **추론** | 일반적인 디자인 시스템 관례와 화면 배열을 바탕으로 해석함 |
| **확인 불가** | JPG만으로는 Figma 내부 구조나 정확한 값까지 검증할 수 없음 |

### 원본 형식에 따른 한계

- 현재 확인 가능한 원본은 편집 가능한 Figma 파일이 아니라 JPG 이미지다.
- 따라서 화면에 적힌 변수명, 크기, Variant 개수는 확인할 수 있지만 Figma Variable의 실제 값과 연결 상태는 열람할 수 없다.
- Primitive Color와 Semantic Color의 **HEX 값은 원본 이미지에 표기되어 있지 않아 확정할 수 없다.** JPG 픽셀을 추출하면 압축과 색상 프로파일의 영향을 받으므로 원본 토큰값으로 간주할 수 없다.
- Auto Layout, Component Property, Instance Swap, Variable Mode, Light/Dark Mode, Responsive Constraint의 실제 설정 여부도 JPG만으로는 확인할 수 없다.
- 아래 분석에서는 이러한 항목을 구현 완료 사실로 단정하지 않고 `명시됨`과 `검증됨`을 분리한다.
- `확정`은 JPG에 표시된 정보가 존재한다는 뜻이며, 해당 기능이 실제 Figma 파일에 설정·연결되어 있다는 뜻은 아니다.
- 상태명이나 Token 연결처럼 이미지에 적혀 있지 않은 내용은 문서 전체에서 `시각 확인` 또는 `추론`으로 취급한다.

## 1. 전체 구성과 설계 방식

### 1.1 페이지 구성

| 번호 | 분류 | 페이지 | 핵심 역할 |
|---:|---|---|---|
| 1 | Intro | 표지 | 시스템의 목적, 범위, 톤 제시 |
| 2 | Intro | Getting Started | Token → Component → Template 사용 순서 안내 |
| 3 | Foundation | Colors | Primitive와 Semantic Color 정의 |
| 4 | Foundation | Typography | 한국어 중심 서체 위계 정의 |
| 5 | Foundation | Spacing & Sizing | 간격, 컨트롤 높이, 핵심 치수 정의 |
| 6 | Foundation | Radius & Effects | 모서리와 Elevation 규칙 정의 |
| 7 | Component | Button | 주요 행동과 상태 표현 |
| 8 | Component | Badge | 상태·난이도·분류 표시 |
| 9 | Component | Progress | 학습·시험 진행률 표시 |
| 10 | Component | Question Number | 문제 이동, 응답, 채점 상태 표시 |
| 11 | Component | Quiz Option | 객관식 선택부터 채점·복습까지 표현 |
| 12 | Component | Timer | 기본·주의·위험 시간 상태 전달 |
| 13 | Component | Card | 정보 유형별 콘텐츠 표면 제공 |

### 1.2 시스템 계층

```text
Foundation
├─ Color: Primitive Token → Semantic Token
├─ Typography
├─ Spacing & Sizing
└─ Radius & Effects
    ↓
Component
    ↓
State / Variant
    ↓
Template
    ↓
Web UI
```

Primitive와 Semantic Color는 Foundation 바깥의 별도 단계가 아니라 Color Foundation 내부의 두 계층이다. 구조의 핵심은 컴포넌트가 원시 색상값을 직접 참조하지 않고, 용도 중심의 Semantic Token을 거쳐 표현되도록 설계한 점이다. 예를 들어 `blue/500 → color/bg/brand → Button 배경` 같은 연결을 의도한 체계로 해석할 수 있다. 단, 이미지에서 확정되는 것은 “컴포넌트에는 Semantic Color만 사용”한다는 설명까지이며, 이 예시의 실제 Token Binding은 Figma 원본 없이는 확인할 수 없다.

### 1.3 페이지 자체의 공통 레이아웃 문법

- 밝은 캔버스 위에 좌측 정렬된 제목, 설명, 메타 정보, 예시 영역이 반복된다.
- 콘텐츠 폭과 좌측 시작선이 거의 일정하여 문서 전체의 탐색성이 좋다.
- 예시는 연한 Gray 계열의 큰 패널 또는 개별 White Surface에 정렬된다.
- 반복 컴포넌트는 행과 열의 규칙적인 Grid로 비교 가능하게 배치된다.
- 시각적 장식보다 명칭, 상태 수, 접근성 기준, 샘플 비교를 우선한다.

## 2.1 1. 표지

### 표시 내용

- `COMMUNITY UI KIT · VERSION 1.0`

- `시험 학습 경험을 위한 웹 기반 디자인 시스템`
- `Foundations · Components · Quiz States · Responsive Templates`
- `Figma Variables · Auto Layout · Light / Dark · Web Responsive`

### 시각 구조

- 화면 전체를 매우 짙은 Navy로 채우고 모든 핵심 정보를 중앙 정렬했다.
- 상단에는 Blue Pill Badge, 중앙에는 대형 White Heading, 하단에는 설명과 기능 범위를 배치했다.
- 얇은 Divider가 제품 설명과 기술 범위를 분리한다.
- 네 모서리의 큰 Radius는 제품 전체의 부드러운 조형 언어를 표지 단계부터 암시한다.

### 해석

- Navy와 White의 강한 대비가 신뢰감, 집중, 시험 환경의 안정성을 만든다.
- Blue는 브랜드 식별과 핵심 인터랙션을 담당하는 주조색으로 예고된다.
- `Quiz States`, `Responsive Templates`, `Light / Dark`가 범위로 명시되어 있으나, 13장 안에는 별도 Template 페이지와 Dark Mode 비교 페이지가 없다.
- 따라서 위 기능들은 **표지상 기획 범위로는 확정**되지만, 제공된 JPG만으로 **실제 구현 범위는 확인 불가**다.

## 2.2 2. Getting Started

### 확정된 3단계

1. **Foundations 선택**  
   컬러·타이포·간격·라운드 토큰을 먼저 선택하고 화면 요소에는 의미 기반 토큰을 사용한다.
2. **Components 조합**  
   Button·Badge·Card·Quiz Option을 Instance로 배치하고 Variants로 상태를 전환한다.
3. **Templates 완성**  
   학습 홈·문제 풀이·결과·오답 화면 패턴을 Desktop·Tablet·Mobile에 적용한다.

### 구조적 의미

이 페이지는 스타일 가이드를 단순한 샘플 모음이 아니라 재사용 가능한 조립 체계로 정의한다. 작업 순서는 `Foundation 선택 → Component 조합 → 반응형 화면 완성`이며, 이후 스타일을 수정할 때도 동일한 순서를 유지해야 일관성이 깨지지 않는다.

## 2.3 3. Foundations — Colors

### 컬러 구조

원본은 `Primitives · Value`와 `Semantic Color · Light / Dark`의 2단계로 구성된다. 설명문에는 “Primitives는 원시 팔레트이고, Semantic Color는 실제 UI 역할을 나타내며 컴포넌트에는 Semantic Color만 사용”한다고 명시되어 있다.

### Primitive Color — 총 27개

| 그룹 | 확인된 토큰 |
|---|---|
| White | `white/1000` |
| Black | `black/1000` |
| Navy | `navy/50`, `navy/100`, `navy/500`, `navy/700`, `navy/900` |
| Blue | `blue/100`, `blue/500`, `blue/600`, `blue/700` |
| Mint | `mint/100`, `mint/500`, `mint/700`, `mint/800` |
| Orange | `orange/100`, `orange/500`, `orange/700`, `orange/800` |
| Red | `red/100`, `red/500`, `red/700` |
| Gray | `gray/50`, `gray/200`, `gray/500`, `gray/700`, `gray/900` |

각 샘플에는 `var(--ace-{색상}-{단계})` 형식의 CSS Variable 표기가 함께 나타난다. 예: `navy/900 → var(--ace-navy-900)`.

### Semantic Color — 총 30개

| 역할군 | 확인된 토큰 |
|---|---|
| Background | `color/bg/canvas`, `surface`, `subtle`, `brand`, `brand-hover`, `inverse`, `success`, `warning`, `danger`, `selected`, `review`, `disabled`, `danger-strong`, `danger-hover`, `success-strong`, `warning-strong` |
| Border | `color/border/default`, `strong`, `brand`, `focus`, `danger` |
| Text | `color/text/primary`, `secondary`, `muted`, `brand`, `on-brand`, `success`, `warning`, `danger` |
| Icon | `color/icon/default` |

Semantic 샘플의 CSS Variable은 대부분 `var(--ace-color-...)` 형태로 표시된다. 다만 `color/bg/warning-strong` 샘플은 JPG에서 토큰명만 보이고 CSS Variable 문자열은 표시되지 않으므로, 해당 변수명의 존재와 정확한 철자는 별도 원본 없이는 확정하지 않는다.

### 의미별 시각 역할

| 색상 계열 | 주된 역할 | 적용 예시 |
|---|---|---|
| Navy | 기본 텍스트, 역상 배경, 높은 정보 위계 | 제목, 기본 Timer, 표지 |
| Blue | 브랜드, 선택, 진행, Focus | Button, Progress, Question Number, Selected Option |
| Mint/Green | 성공, 정답, 결과 | Correct Option, Success Progress, Result Card |
| Orange | 경고, 복습 | Warning Timer, Review Option |
| Red | 오류, 오답, 위험 행동 | Danger Button, Incorrect Option, Danger Timer |
| Gray | 캔버스, 경계, 비활성, 보조 정보 | Disabled, Track, 기본 Border |

위 표의 색상 역할 중 Colors 페이지에 직접 적힌 것은 Token의 역할명이다. Question Number·Quiz Option·Card 등에 대한 구체적인 적용 예시는 각 컴포넌트의 색상 표현을 대조한 **시각적 대응 해석**이며, 실제 Figma Token Binding을 확인한 결과는 아니다.

### 검증 결과와 주의점

- 1차 분석에서 언급된 계열과 Semantic Token은 원본에서 확인된다.
- 다만 각 토큰의 HEX 값 및 `Semantic → Primitive` 실제 매핑은 이미지에 표시되지 않는다.
- 제목의 `Light / Dark` 표기는 Mode 존재 가능성을 보여주지만, 페이지에는 Light와 Dark 값을 나란히 비교하는 표나 Mode별 값이 없다. 따라서 Dark Mode 토큰 정의가 실제로 완성됐다고 단정할 수 없다.
- `focus`와 일반 `brand`가 시각적으로 유사하므로 실제 접근성 검토 시 구별성과 대비를 수치로 확인해야 한다.

## 2.4 4. Foundations — Typography

### 기본 원칙

- 단일 서체군: **Noto Sans KR**
- 한국어 가독성과 학습 집중도를 우선한다.
- 화면 목적에 맞는 스타일을 선택하고 임의 크기 사용을 피하도록 명시한다.

### 확정된 타입 스케일 — 총 13개

| Token | Weight | Size | Line height | 대표 용도 |
|---|---|---:|---:|---|
| Display/Large | Bold | 48px | 60px | 핵심 메시지, Hero |
| Heading/1 | Bold | 36px | 48px | 최상위 페이지 제목 |
| Heading/2 | Bold | 28px | 40px | 주요 섹션 제목 |
| Heading/3 | Bold | 22px | 32px | 하위 섹션 제목 |
| Title/Large | Bold | 20px | 28px | Card·Component 제목 |
| Title/Medium | Medium | 18px | 26px | 중간 위계 제목 |
| Body/Large | Regular | 16px | 24px | 주요 본문 |
| Body/Medium | Regular | 14px | 22px | 일반 본문 |
| Body/Small | Regular | 13px | 20px | 보조 본문 |
| Label/Large | Medium | 14px | 20px | Button 등 UI Label |
| Label/Medium | Medium | 12px | 18px | Badge·소형 Label |
| Caption | Regular | 11px | 16px | 부가 정보 |
| Timer | Bold | 20px | 28px | 시간 정보 전용 |

### 분석

- Display부터 Caption까지 역할별 위계가 명확하며, 크기뿐 아니라 Weight와 Line Height도 함께 정의되어 있다.
- 한국어 본문 Line Height가 글자 크기의 약 1.5배 수준이라 밀도가 지나치게 높지 않다.
- Timer는 Title/Large와 같은 20/28/Bold이지만 의미가 다른 별도 토큰이다. 현재 값이 같아도 향후 시험 특화 표현만 독립 수정할 수 있다.
- Button과 Badge에 사용되는 정확한 Typography Token 바인딩은 JPG만으로 확인할 수 없다.

## 2.5 5. Foundations — Spacing & Sizing

### Spacing Scale — 총 11개

`0, 4, 8, 12, 16, 20, 24, 32, 40, 48, 64px`

각 값은 `spacing/{값}`과 `var(--ace-spacing-{값})` 형식으로 표시된다. 설명은 8px 기반 간격과 공통 컨트롤 높이를 사용해 화면 밀도와 터치 영역을 일관되게 유지한다고 밝힌다. 실제 Scale에는 4px 보정 단위도 포함되어 있으므로 정확히는 **8px 중심 + 4px 세부 단위 시스템**이다.

### Control & Touch Size

| Token | 값 | 의미 |
|---|---:|---|
| `size/control/small` | 32px | 소형 컨트롤 |
| `size/control/medium` | 40px | 기본 컨트롤 |
| `size/control/large` | 48px | 대형 컨트롤 |
| `size/touch/minimum` | 44px | 최소 터치 영역 |

### Component Metrics

| Token | 값 | 적용 목적 |
|---|---:|---|
| `stroke/1` | 1px | 일반 경계선 |
| `stroke/2` | 2px | Focus·강조 경계선 |
| `size/badge/small` | 24px | 소형 Badge 높이 |
| `size/progress/track` | 12px | Progress Track 높이 |
| `size/option/minimum` | 64px | Quiz Option 최소 높이 |

### 분석 및 점검점

- 간격과 컨트롤 규격이 하나의 페이지에서 함께 관리돼 컴포넌트 밀도를 통제하기 좋다.
- `control/medium 40px`과 `touch/minimum 44px`이 별도로 존재한다. 40px Button을 터치 환경에서 사용할 경우 보이지 않는 Hit Area를 44px 이상 확보하는지 확인해야 한다.
- Question Number 페이지에는 “최소 40px 터치 영역”이 적혀 있어 Foundation의 44px 최소 터치 기준과 불일치한다. 이후 실제 제작 단계에서 **전역 기준을 44px로 통일할지**, 마우스 중심 CBT 환경의 예외로 40px을 허용할지 결정해야 한다.

## 2.6 6. Foundations — Radius & Effects

### Radius Scale

| Token | 값 |
|---|---:|
| `radius/0` | 0px |
| `radius/4` | 4px |
| `radius/8` | 8px |
| `radius/12` | 12px |
| `radius/16` | 16px |
| `radius/24` | 24px |
| `radius/full` | Pill |

### Shadow Styles

| Style | Y | Blur | Opacity | 용도 해석 |
|---|---:|---:|---:|---|
| `AI ACE CBT/Shadow/Card` | 2 | 8 | 8% | 일반 카드와 낮은 표면 |
| `AI ACE CBT/Shadow/Floating` | 8 | 24 | 12% | 떠 있는 메뉴·보조 UI |
| `AI ACE CBT/Shadow/Overlay` | 16 | 40 | 16% | Modal·Overlay 계층 |

### 분석

- Button과 Quiz Option은 중간 Radius, Badge와 Question Number는 Full Radius, Card는 큰 Radius를 사용하는 계층이 시각적으로 확인된다.
- Shadow가 강하지 않아 Border와 배경색이 표면 구분의 중심이다.
- Y, Blur, Opacity는 확인되지만 그림자 색상과 X Offset은 표기되지 않는다.
- Foundation 설명에는 Radius를 “공통 변수”, 그림자를 “Effect Style”로 관리한다고 명시된다. 실제 등록 및 연결 여부는 Figma 원본 없이는 확인 불가다.

## 2.7 7. Components — Button

### 확정 구조

- Property: `Label`
- Variants: `Size / Style / State`
- Size 2종 × Style 3종 × State 4종 = **총 24 Variants**
- Accessibility: `Focus 2px`, `최소 높이 40px`

### 시각적으로 확인되는 체계

- 행은 두 Size 그룹 안에서 Blue Filled, Blue Outline, Red Filled의 3 Style로 배열된다.
- 열은 4개 상태로 구성되며 시각상 기본, 더 진한 상호작용, 2px Focus, Disabled 순으로 해석된다.
- Filled Button은 White Label, Outline Button은 Blue Label, Danger Button은 White Label을 사용한다.
- Disabled에서는 Style 차이가 사라지고 Gray Background와 Muted Text로 수렴한다.

### 정확성 구분

- `Size / Style / State`라는 Property 축과 24개 개수는 확정이다.
- `Primary`, `Outline`, `Danger` 및 `Default`, `Hover`, `Focus`, `Disabled`라는 이름은 화면에 직접 적혀 있지 않으므로 기능적 해석이다. Figma 내부 Property 명칭으로 단정하면 안 된다.

### 평가

- 강한 행동, 보조 행동, 위험 행동이 역할별로 분리되어 있다.
- Focus를 색상 변화만이 아니라 2px Stroke로 표현해 키보드 탐색에 유리하다.
- Danger Focus에서 Blue 외곽선과 Red 내부가 함께 나타나는데, 시스템 공통 Focus Color를 유지한 결과로 해석된다.
- 아이콘 포함, 로딩, 전체 너비, 아이콘 전용 Button은 이 페이지에서 확인되지 않는다.

## 2.8 8. Components — Badge

### 확정 구조

- Property: `Label`
- Variants: `Size / Tone`
- Size 2종 × Tone 5종 = **총 10 Variants**
- 짧은 명사형 문구 사용

### 시각적 Tone

왼쪽부터 Neutral, Brand, Success, Warning, Danger에 대응하는 것으로 해석된다. 모두 낮은 채도의 밝은 Background, 의미 색상의 Text/Border, Full Radius를 사용해 Button보다 낮은 행동 위계를 유지한다.

### 평가

- 상태·난이도·분류처럼 짧고 보조적인 정보를 빠르게 스캔하기 좋다.
- Tone의 실제 Property 값 명칭은 화면에 표시되지 않는다.
- 아이콘형, Dot형, 제거 가능한 Badge 등은 확인되지 않는다.

## 2.9 9. Components — Progress

### 확정 구조

- Variants: `Value / Tone`
- Value 5단계 × Tone 2종 = **총 10 Variants**
- 단계 전환 시 값과 완료 Tone을 함께 변경하도록 안내한다.
- Foundation 기준 Track 높이: 12px

### 시각 체계

- Value는 빈 상태에서 시작해 약 25%, 50%, 75%, 100%로 증가하는 5단계로 보인다.
- Tone은 Blue Brand와 Green Success 두 줄로 제시된다.
- Track은 밝은 Gray, Fill은 의미색, 양 끝은 둥근 형태다.

### 확인 필요

- 실제 Value Property 값이 `0/25/50/75/100`인지 다른 단계명인지는 표기되지 않아 추론에 해당한다.
- 정확한 퍼센트 표시, ARIA 값, Animation, Indeterminate 상태는 확인되지 않는다.
- 색상만으로 Brand와 Success를 구별하므로 실제 화면에서는 텍스트 수치나 완료 Label을 함께 제공하는 편이 접근성에 유리하다.

## 2.10 10. Components — Question Number

### 확정 구조

- Property: `Number`
- Variants: `Size / State`
- Size 2종 × State 6종 = **총 12 Variants**
- 최소 40px 터치 영역 유지

### 시각적으로 확인되는 6개 상태

1. White Surface + 기본 Border
2. Blue Filled + White Text
3. Blue Outline + Blue Text
4. Mint Background + Green Text
5. Light Red Background + Red Border/Text
6. Light Orange Background + Orange Text

기능상 각각 기본, 현재/선택, 응답/Focus, 정답, 오답, 복습에 대응할 가능성이 높다. 단, 정확한 State 명칭은 원본 이미지에 적혀 있지 않다.

### 평가

- 원형 Fill·Border·Text 조합으로 문제의 위치와 상태를 작은 면적 안에 압축한다.
- State 6종이 색상에 크게 의존하므로 정답/오답/복습은 아이콘, Tooltip, 범례 또는 별도 Label 보완이 필요할 수 있다.
- 해당 페이지의 40px 터치 기준은 Foundation의 `size/touch/minimum 44px`과 조정이 필요하다.

## 2.11 11. Components — Quiz Option

### 확정 구조

- 총 **8 States**
- `Prefix/Label` 편집 가능
- 최소 높이 64px
- Focus 2px
- 객관식 선택, 채점, 복습 상태를 하나의 컴포넌트로 관리

### 공통 Anatomy

- 전체 Container
- 원형 또는 문자형 Prefix 영역
- `A`와 같은 선택지 Label
- 선택지 본문
- Border, Background, Text Color

### 시각적으로 확인되는 8개 상태

| 순서 | 시각 표현 | 기능적 해석 |
|---:|---|---|
| 1 | White + Gray Border + 연한 Prefix | Default |
| 2 | White + Blue Border + Blue Prefix Outline | Hover/Interaction |
| 3 | White + 두꺼운 Blue Border + Blue Filled Prefix | Focus |
| 4 | Light Blue Background + Blue Border/Text/Prefix | Selected |
| 5 | Light Mint Background + Green Text/Prefix | Correct |
| 6 | Light Red Background + Red Border/Text/Prefix | Incorrect |
| 7 | Gray Background + Muted Text + 단순 Prefix | Disabled |
| 8 | Light Orange Background + Orange Text/Prefix | Review |

위 상태명은 시각적 기능을 설명하기 위한 분석 명칭이며, Figma의 실제 State Property 값은 확인할 수 없다.

### 평가

- 현재 시스템에서 상태 변화가 가장 복잡하고 CBT 도메인 특성이 가장 강한 핵심 컴포넌트다.
- Prefix, Border, Background, Text를 함께 바꾸므로 단일 색상 변화보다 상태 인지가 쉽다.
- 선택과 Focus가 서로 다른 상태로 보이지만, 실제 사용에서는 `Selected + Focus` 같은 복합 상태가 필요한지 확인해야 한다.
- 정답과 오답을 색으로만 전달하지 않도록 체크·엑스 아이콘이나 보조 문구를 추가할 가능성을 열어두는 것이 좋다.

## 2.12 12. Components — Timer

### 확정 구조

- `Default · Warning · Danger`
- Time 편집 가능
- 시험 제한 시간과 임박·위험 상태 전달
- 전용 Typography: Noto Sans KR Bold, 20px/28px

### 상태 표현

| State | Background/Border/Text | 의미 |
|---|---|---|
| Default | White, Gray Border, Navy Text | 정상 시간 |
| Warning | Light Orange, 연한 Border, Orange Text | 시간 임박 |
| Danger | Light Red, Red Border, Red Text | 긴급·위험 |

### 평가

- Pill Container와 굵은 숫자가 작은 영역에서도 즉시 읽힌다.
- Warning과 Danger는 배경·경계·텍스트가 동시에 바뀌어 단계가 분명하다.
- 스크린리더 공지 주기, 점멸 여부, 아이콘·문구 보조는 확인되지 않는다. 시간 압박을 과도하게 높이는 Animation은 신중하게 사용해야 한다.

## 2.13 13. Components — Card

### 확정 구조

- Variants: `Base · Stat · Explanation · Result`
- `Title/Body` 편집 가능
- 대시보드 통계, 해설, 결과 정보를 일관된 표면 위에 구성

### 공통 Anatomy

- 작은 영문 Category Label
- `카드 제목`
- 설명 Body
- Rounded Container

### Variant별 표현

| Variant | 표현 | 의미 위계 |
|---|---|---|
| Base | White Surface + 기본 Shadow | 일반 정보 |
| Stat | White + Blue Border + Blue Label/Title | 주요 통계·강조 |
| Explanation | Light Blue Background + Blue Border/Title | 해설·학습 정보 |
| Result | Light Mint Background + Green Label/Title | 결과·성공 정보 |

### 평가

- 공통 Anatomy를 유지하면서 Semantic Color로 정보 유형을 구분한다.
- Base와 Result에는 Shadow가 시각적으로 보이고, Stat/Explanation은 Border의 비중이 더 높다.
- 실제 Padding, 최소/고정 높이, 반응형 Width, Slot 구조는 표시되지 않는다.
- Warning·Danger Card Variant는 현재 범위에서 확인되지 않는다.

## 3. Foundation과 Component 연결 관계

| Foundation | 직접 영향을 받는 요소 | 대표 연결 사례 |
|---|---|---|
| Color | 전 컴포넌트 | Brand→Button/Progress, Success→Correct/Result, Warning→Review/Timer, Danger→Incorrect/Timer *(컴포넌트 적용명은 일부 추론)* |
| Typography | 제목, 본문, Label, Timer | Label→Button/Badge, Timer→시간 정보, Title→Card |
| Spacing | 내부 Padding, 항목 간 Gap, Section 간격 | Quiz Option 내부 간격, Card 콘텐츠 간격 |
| Sizing | Button, Badge, Progress, Question Number, Quiz Option | 40px Button, 24px Badge, 12px Track, 64px Option |
| Radius | Button, Badge, Number, Option, Timer, Card | 상태보다 전체 브랜드 인상을 좌우 |
| Effects | Card 및 상위 Layer | Card→Floating→Overlay 순 Elevation 증가 |

### 대표 상태 연결 — 시각적 대응 해석

아래 연결은 Colors 페이지의 의미 기반 Token 명칭과 각 컴포넌트 샘플의 색상·배경·경계 표현을 서로 대조한 결과다. 실제 Figma Variable Binding이나 State Property 값을 열람한 결과가 아니므로, `Timer`와 `Card`처럼 명칭이 화면에 직접 표시된 경우를 제외한 상태명은 기능적 해석으로 본다.

```text
Brand Blue
├─ Button의 주요 행동
├─ Progress의 진행 Fill
├─ Question Number의 현재/선택 상태
├─ Quiz Option의 상호작용·선택 상태
└─ Stat·Explanation Card

Mint/Green
├─ Progress 완료 Tone
├─ Question Number 정답 상태
├─ Quiz Option Correct
└─ Result Card

Orange
├─ Question Number 복습 상태
├─ Quiz Option Review
└─ Timer Warning

Red
├─ Danger Button
├─ Question Number 오답 상태
├─ Quiz Option Incorrect
└─ Timer Danger
```

이 연결 때문에 이후 선호 디자인을 적용할 때 개별 컴포넌트의 색을 각각 바꾸기보다 Primitive와 Semantic 역할을 먼저 조정해야 한다.

## 4. 전체 시각 언어 분석

### Color

- Navy + Blue가 브랜드와 정보 위계의 중심이다.
- White/Light Gray 면적이 넓어 화면이 밝고 안정적이다.
- Mint, Orange, Red가 정답·복습·오답처럼 교육 서비스의 상태 의미를 담당한다.
- 상태색은 대체로 진한 전경색과 매우 옅은 배경색을 짝지어 사용한다.

### Typography

- Noto Sans KR 단일 계열로 한국어 가독성과 일관성을 확보한다.
- Bold 제목과 Regular 본문의 대비가 명확하다.
- UI Label에는 Medium을 사용해 작은 크기에서도 형태가 유지된다.

### Shape

- Rounded Rectangle과 Pill을 적극 사용한다.
- Sharp한 모서리보다 8~16px Radius가 중심이며, 상태 Label과 숫자에는 Full Radius를 사용한다.
- 교육·시험 서비스가 줄 수 있는 긴장감을 완화하는 부드러운 형태다.

### Effect와 Surface

- Shadow는 낮은 Opacity를 사용하고 Border·Tint Background가 표면 분리의 중심이다.
- 과도한 입체감이나 장식이 없어 정보량이 많은 학습 화면에 적합하다.

### Layout와 Mood

- 넓은 여백, 좌측 정렬, 반복 Grid, 일정한 패널 구조가 중심이다.
- 전체 인상은 Clean, Modern, Functional, Educational, SaaS형이다.
- 브랜드 개성은 강하지 않지만 안정적이며 확장 가능한 기본형 디자인이다.

## 5. 강점

1. Primitive와 Semantic Color의 역할이 분리되어 있어 전체 테마 변경에 유리하다.
2. Typography가 용도별로 세분되고 크기·Weight·Line Height가 함께 정의되어 있다.
3. 8px 중심의 간격과 4px 보정 단위가 밀도 조절에 유연하다.
4. 컨트롤 높이, Touch Area, Stroke, Option 최소 높이까지 수치화돼 있다.
5. Radius와 Shadow가 단계별 Token/Style로 정의되어 있다.
6. 컴포넌트가 Size·Style·Tone·State 축으로 체계화돼 있다.
7. Brand·Success·Warning·Danger에 대응하는 시각 표현이 여러 컴포넌트에서 일관되게 반복되는 것으로 보인다. 실제 Token Binding은 확인 불가다.
8. Question Number, Quiz Option, Timer처럼 CBT에 필요한 전용 컴포넌트가 있다.
9. Focus 2px, 최소 높이, 최소 Touch Area 등 접근성 기준을 일부 명시한다.
10. Foundation의 변경을 여러 컴포넌트로 확장하기 좋은 구조다.
11. 문서 페이지 자체도 동일한 Grid와 위계를 사용해 가이드의 전달력이 좋다.

## 6. 보완점과 잠재적 위험

### 6.1 문서에서 확인되지 않는 구현 정보

- 정확한 HEX/RGBA 값
- Semantic Token과 Primitive Token의 실제 연결표
- Dark Mode별 Token 값과 적용 결과
- 각 Variant Property의 정확한 값 명칭
- Auto Layout 방향, Padding, Gap, Hug/Fill 설정
- Responsive Constraint와 Breakpoint
- Component Property 및 내부 Layer 구조
- Focus 순서, Keyboard Interaction, ARIA 규칙

### 6.2 규칙 간 충돌

- Foundation은 최소 Touch Size를 44px로 제시하지만 Question Number는 최소 40px 터치 영역을 명시한다.
- Button은 최소 높이 40px이므로 모바일/터치 환경에서는 별도 Hit Area 규칙이 필요하다.

### 6.3 접근성 점검 필요

- 여러 상태가 색상에 의존한다. Correct/Incorrect/Review는 아이콘이나 텍스트 보조 수단을 검토해야 한다.
- HEX 값이 없어 WCAG 대비율을 계산할 수 없다.
- Caption 11px은 부가 정보용으로 제한하고 핵심 정보에는 사용하지 않는 편이 안전하다.
- Progress는 색상 외에 값/완료 상태를 텍스트로 제공할 필요가 있다.
- Timer의 상태 변화는 색상만이 아니라 문구나 보조 기술 공지를 고려해야 한다.

### 6.4 컴포넌트 범위의 공백

- Button의 아이콘, 로딩, Full Width 상태
- Quiz Option의 복합 상태(Selected+Focus, Correct+Focus 등)
- Progress의 수치 Label과 Indeterminate 상태
- Card의 Warning/Danger 유형
- Form Input, Checkbox, Radio, Modal, Navigation 등 실제 완성 화면에 필요한 공통 요소

이 항목들은 현재 스타일 가이드의 오류라고 단정할 수 없으며, 제공된 13장 범위에서 확인되지 않는 확장 후보다.

제공된 1차 분석의 핵심 판단, 즉 **기존 시스템 구조를 파괴하지 않고 Token과 Semantic 관계를 유지한 채 선호 디자인을 Foundation부터 적용해야 한다**는 결론은 타당하다.

재검토를 통해 다음 내용을 추가로 명확히 했다.

1. JPG 13장을 파일별로 개별 재대조했으며, 각 결과를 아래 검수표에 기록했다.
2. Primitive 27개, Semantic Color 30개, Typography 13개, Spacing 11개가 이미지에서 확인된다.
3. Primitive와 Semantic Color는 별도 Foundation 이전 단계가 아니라 Color Foundation 내부의 두 계층으로 정리하는 것이 정확하다.
4. Component별 Variant 축과 개수는 확인되지만 일부 State/Tone의 실제 Property 명칭은 화면에 없어 기능적 추론과 구분해야 한다.
5. `Light/Dark`, `Responsive Templates`, `Figma Variables`, `Auto Layout`은 표지와 안내에 명시되지만 실제 구현은 JPG만으로 검증되지 않는다.
6. 정확한 HEX 값과 Token Binding은 편집 가능한 원본 또는 별도 명세가 있어야 확정할 수 있다.
7. Touch Minimum 44px과 Question Number의 40px 기준 사이에 정합성 검토가 필요하다.
8. 상태색 의존도를 낮추기 위한 아이콘·문구·범례 등 접근성 보완 가능성이 있다.

따라서 다음 단계에서는 본 문서를 구조 기준으로 사용하고, 사용자가 제공할 선호 디자인 레퍼런스에서 색상, 서체, Radius, Surface, 밀도 등의 시각 특징을 추출한 뒤 **Foundation 정비(Color는 Primitive → Semantic) → Component → State/Variant → Template/Web UI** 순서로 적용하는 것이 적절하다.

현재 단계에서는 디자인 및 원본 파일을 수정하지 않았다.
