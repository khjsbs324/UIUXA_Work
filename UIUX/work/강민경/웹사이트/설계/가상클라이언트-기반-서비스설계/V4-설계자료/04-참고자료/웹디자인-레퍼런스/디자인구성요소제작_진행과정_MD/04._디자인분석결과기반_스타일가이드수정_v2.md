# LOVE 웹디자인 레퍼런스 기반 스타일가이드 수정 기준서 v2

- 문서 목적: 선호 레퍼런스의 시각 표현뿐 아니라 기능, 사용자 흐름, 상호작용, 상태, 반응형 및 접근성을 분석하여 스타일가이드 수정 규칙으로 전환한다.
- 작성 기준일: 2026-08-20
- 적용 대상: DAMORI 브랜드 기반 스타일가이드 초안 및 웹디자인 초안의 후속 개선
- 원본 보호: 원본 평가자료, 브랜드 기획 자료, 기존 분석 문서와 기존 PNG·HTML은 수정하지 않는다.
- 결과 성격: 최종 시안 자체가 아니라 다음 디자인 결정을 위한 근거·명세 문서다.

## 0. v2에서 달라지는 점

기존 문서는 레퍼런스의 성격과 시각 선호를 유효하게 정리했지만, 일부 링크는 정적 캡처나 프로젝트 설명에 의존하여 실제 기능과 상태를 충분히 분해하지 못했다. v2는 다음을 추가한다.

1. 레퍼런스별 `목적 → 사용자 행동 → 기능 → UI 패턴 → 상태 → 시각 표현`을 연결한다.
2. 확인된 사실, 합리적 추론, 확인 불가 항목을 구분한다.
3. 기능을 그대로 복제하지 않고 DAMORI MVP의 문제 해결에 필요한 원리만 추출한다.
4. Foundation, Component, Pattern, Page의 네 층으로 적용 위치를 명시한다.
5. 정상 상태뿐 아니라 Empty, Pending, Error, Local, Conflict, Hold 상태를 설계한다.
6. Desktop 화면의 미관뿐 아니라 Mobile 재배열, Keyboard, Focus, Reduced Motion을 검증한다.
7. 13장 스타일가이드 각각에 입력값, 수정 항목, 검증 기준과 금지 항목을 제공한다.

### 0.1 핵심 결론

> DAMORI에 적합한 방향은 따뜻한 Editorial 브랜드 표현과 예측 가능한 기능 UI의 결합이다. 감성은 큰 이미지, 타이포그래피, 여백, 재료감과 제한된 모션에서 만들고, 선택·입력·저장·복귀 기능은 일관된 컴포넌트와 명시적인 상태로 작동해야 한다.

## 2. 프로젝트의 기능 기준선

### 2.1 사용자와 문제

핵심 사용자는 기록 도구에 관심이 있지만 고정 양식, 과도한 기능, 연속 기록 압박과 선택 피로 때문에 중단 경험이 있는 사람이다. 따라서 디자인은 사용자를 평가하거나 성취를 압박해서는 안 된다.

핵심 문제는 다음과 같다.

- 무엇으로 어떻게 기록할지 선택하기 어렵다.
- 빈 화면 또는 빈 노트 앞에서 시작 부담이 크다.
- Analog와 Digital의 장단점을 비교하기 어렵다.
- 중단 후 밀린 기록을 모두 처리해야 한다고 느낀다.
- 저장, 원본, 사본, 보류와 미지원 상태를 오해할 수 있다.

### 2.2 MVP 핵심 과업

| 과업 | 사용자가 알아야 하는 것 | 필요한 UI 패턴 |
|---|---|---|
| 방식 찾기 | 추천은 수정 가능한 초안이며 직접 탐색도 가능 | Stepper, Option, 이유 설명, 건너뛰기 |
| Analog/Digital 비교 | 어느 하나가 정답이 아니며 조건이 다름 | 비교표, 조건 Badge, 상세 Disclosure |
| 작은 시작 | 한 줄·사진·음성·기분 중 편한 단위를 선택 | Tab 또는 Segmented Control, Input, 상태 안내 |
| 템플릿 미리보기 | 구조와 표현, 원본과 사본이 다름 | Preview, Apply/Cancel, 원본 보호 문구 |
| 중단 후 복귀 | 지금 하기·보류·나누기·새 기록이 모두 가능 | Recovery Choice, 부담 없는 카피 |
| 상태 이해 | 현재 가능한 범위와 보존 상태 | Inline Status, Badge, Recovery Action |

### 2.3 구현하지 않는 기능

다음은 시각적으로 그럴듯해도 활성 기능처럼 만들지 않는다.

- 회원가입·로그인·마이페이지
- 서버·클라우드 저장과 자동 동기화
- AI 자동 추천·분류
- 외부 달력·알림 연동
- 실제 업로드·백업·복구·내보내기
- 가격·재고·결제·배송
- 유료 마켓과 커뮤니티

## 3. 레퍼런스 분석 프레임

각 링크는 다음 12개 질문으로 분석한다.

1. 사이트의 목적과 주요 사용자는 누구인가?
2. 사용자가 처음 이해해야 할 것은 무엇인가?
3. 가장 중요한 행동과 보조 행동은 무엇인가?
4. 탐색, 비교, 선택, 입력, 저장, 복귀 흐름은 어떻게 이어지는가?
5. 정보가 어떤 Section과 Module로 분해되는가?
6. Header, Search, Filter, Tab, Card, Form은 어떤 역할인가?
7. Default, Hover, Focus, Active, Selected, Disabled 상태가 구분되는가?
8. Empty, Loading, Error, Completion 상태가 있는가?
9. Typography, Image, Color, Shape, Motion이 기능 이해에 기여하는가?
10. Mobile에서 순서와 조작 방식이 어떻게 바뀌어야 하는가?
11. DAMORI 문제와 직접 연결되는 원리는 무엇인가?
12. 맥락이 달라 가져오면 안 되는 것은 무엇인가?

### 4.3 기능 그룹에서 도출한 공통 규칙

1. 첫 화면은 모든 기능을 보여주는 Dashboard가 아니라 목적, 선택권, 첫 행동을 설명한다.
2. 추천에는 결과뿐 아니라 이유, 수정, 건너뛰기와 직접 탐색이 있어야 한다.
3. 비교 정보는 같은 항목과 같은 순서로 정렬해야 한다.
4. 상태는 Toast 하나로 끝내지 않고 해당 입력·기록 주변에 남겨야 한다.
5. 긴 설명은 문제, 선택 기준, 예시, 행동으로 분해한다.
6. 탐색 Card와 Editorial Section을 역할별로 구분한다.
7. 사용자가 중단하거나 뒤로 가도 입력과 선택의 보존 범위를 알려야 한다.

### 5.3 참고용 그룹이 만드는 경계

참고용 사례는 버리는 자료가 아니라 과잉과 평범함의 경계를 정하는 자료다.

- LOOP: 기능 구조는 강하게 참고하되 시각 톤은 중립 비교안으로 둔다.
- Sacheu: Mobile-first와 전환 구조는 참고하되 구매 중심 밀도는 제외한다.
- 서울리빙디자인페어: 다채로운 Illustration이 곧 선호를 의미하지 않는다.
- 국회부산도서관 어린이 사이트: 친근함과 높은 정보량이 동시에 있으면 밀도 통제가 필요하다.
- 상상마당: 콘텐츠 다양성을 Card 반복만으로 해결하지 않는다.
- 비앙글로: Beige, Serif, 여백만으로 고유한 Art Direction이 완성되지는 않는다.

## 6. 종합 디자인 방향

### 6.1 선택한 방향

`Calm Editorial Utility`

- Calm: 사용자를 재촉하지 않는 여백, 낮은 채도, 차분한 상태 피드백
- Editorial: 큰 제목, 이미지와 텍스트의 크기 차이, Section별 리듬
- Utility: 탐색·비교·선택·입력·복귀가 예측 가능한 컴포넌트

### 6.2 이중 레이어 원칙

| 레이어 | 목적 | 허용 표현 | 제한 |
|---|---|---|---|
| Brand/Editorial | 브랜드 기억, 맥락, 감정적 진입 | Display Type, 큰 이미지, 유기적 Shape, 제한된 Motion | 핵심 상태·조작을 대신하지 않음 |
| Functional UI | 이해, 선택, 입력, 상태 복구 | Sans, 명확한 Border, 일관된 Radius, Inline Feedback | 장식적 Type·복잡한 Motion 금지 |

두 레이어는 다른 사이트처럼 보여서는 안 된다. 공통 Canvas, Ink, Spacing, Grid와 Type Scale을 공유한다.

### 6.3 페이지 리듬

```text
집중: Hero 한 문장 + 주 행동
이해: 문제와 방식 설명
선택: 비교·질문·직접 탐색
행동: 작은 기록 시작
안심: 원본·사본·보존 범위
복귀: 중단 후 가능한 선택
제한: PROTOTYPE·LOCAL·HOLD 투명 안내
```

## 7. Foundation v2 수정 명세

### 7.1 Color

#### 역할 구조

| 역할 | 후보값 | 사용 | 금지 |
|---|---:|---|---|
| Canvas | `#F7F3E8` | 전체 기본 배경 | 비활성 상태 의미로 사용 |
| Surface | `#FFFCF5` | 기능 UI, 입력 Surface | 모든 Section의 Card화 |
| Subtle | `#ECE5D5` | 구획·보조 배경 | 저대비 본문 배경 |
| Selection | `#E5EBDD` | 선택된 Option 보조면 | Success 의미 |
| Brand | `#4F603F` | Primary Action, Brand Emphasis | Success와 혼용 |
| Brand Hover | `#3E4D31` | Pointer Hover | Keyboard Focus 대체 |
| Sage | `#71815D`, `#B8C5A9` | 장식·보조 그래픽 | 성공 상태 |
| Clay | `#8B5A46`, `#F2E1D8` | Warm Accent | Error 상태 |
| Ink | `#25281F` | 제목·본문 | 장식 배경의 저대비 조합 |
| Secondary | `#4B5145` | 설명 | 작은 Caption 무분별 사용 |
| Muted | `#686E62` | 보조 정보 | 16px 미만에서 대비 미검증 사용 |
| Focus | `#2457A7` | Focus Ring | Brand Color로 대체 |

#### 상태색 원칙

- Brand, Success, Warning, Danger, Focus를 독립 Semantic Token으로 둔다.
- 색만으로 상태를 전달하지 않고 Icon, Label, 문장을 함께 사용한다.
- `LOCAL`, `PENDING`, `CONFLICT`, `HOLD`는 전통적인 성공·오류만으로 축약하지 않는다.
- 텍스트 대비는 일반 텍스트 4.5:1 이상, 큰 텍스트 3:1 이상을 목표로 한다.
- UI 경계와 Focus Indicator는 인접 색 대비 3:1 이상을 검증한다.

### 7.2 Typography

| 역할 | 방향 | 사용 규칙 |
|---|---|---|
| Display | Noto Serif KR 후보 | Hero·About의 짧은 제목, 2~3행 이하 |
| Heading | Pretendard/Noto Sans KR | 기능 Section과 Card 제목 |
| Body | Pretendard/Noto Sans KR | 16px 이상, line-height 약 1.6, 65ch 이하 |
| Label | Sans Medium/Semibold | Button, Tab, Badge, 상태 이름 |
| Numeric | Inter/Pretendard | 시간·단계·상태 수치, tabular 숫자 검토 |
| Decorative | 라이선스 확인된 손글씨 후보 | 12자 이내, 비필수 장식만 |

Display Type은 분위기를 만들지만 기능 이해를 담당하지 않는다. 모바일에서 글자 크기만 줄이지 말고 줄바꿈, 최대 폭, Section 여백을 함께 바꾼다.

### 7.3 Spacing, Grid, Density

- Core spacing은 4/8px 계열을 유지한다.
- 기능 컴포넌트 내부: 8, 12, 16, 24px 중심
- 기능 그룹 간: 24, 32, 40px
- Section: 64, 80, 96, 120px 후보
- Desktop max-width: 1200~1280px 후보, 본문 읽기 폭은 별도 제한
- 기능 영역은 밀도 있게, Editorial 영역은 넓게 구성한다.
- Mobile은 열 수를 줄이고 DOM/의미 순서를 유지한다.

### 7.4 Radius, Border, Effects

- Control: 8~12px 후보
- Functional Card: 12~16px 후보
- Editorial Image: 0, 16, 비정형 Crop을 목적별 비교
- Pill은 Badge, Filter, 짧은 Toggle에만 사용
- Shadow는 Floating/Overlay 또는 실제 깊이 구분에만 사용
- 일반 Card는 Border, Surface 차이, 여백으로 구분
- 종이·패브릭 Texture는 Hero·About의 2~4% 강도 후보이며 입력 영역에는 사용하지 않는다.

### 7.5 Motion

| 목적 | 허용 예 | 금지 예 |
|---|---|---|
| 상태 피드백 | 선택 표시, Inline Status 전환 | 정보 없는 Bounce |
| 맥락 전환 | Preview 열기, Section 진입 | 긴 페이지 전체 Parallax |
| 시선 유도 | 다음 단계의 짧은 강조 | CTA 무한 반복 |
| 공간 이해 | Drawer, Accordion, Tab Panel | DOM 순서와 다른 이동 |

- 기본 전환 후보: 160~240ms
- 큰 Section 전환 후보: 300~500ms
- `prefers-reduced-motion`에서는 이동·Parallax를 제거하고 Opacity 또는 즉시 전환한다.
- Motion이 없어도 상태와 정보가 동일하게 이해되어야 한다.

## 8. Component v2 수정 명세

### 8.1 Button

- 계층: Primary, Secondary, Tertiary/Text, Destructive
- 상태: Default, Hover, Focus-visible, Pressed, Disabled, Loading
- 최소 Hit Area: 44×44px
- Loading 중 Label 폭을 유지하고 중복 실행을 방지한다.
- Primary는 Section당 원칙적으로 하나로 제한한다.
- `저장됨`처럼 결과 상태를 Button Label만 바꿔 전달하지 않는다.

### 8.2 Badge

- 의미 후보: `PROTOTYPE`, `LOCAL`, `PENDING`, `CONFLICT`, `HOLD`, `UNVERIFIED`
- Badge는 짧은 상태명이고, 필요한 경우 옆에 설명과 행동을 둔다.
- Olive와 Sage를 Success로 오인시키지 않는다.
- 상태명은 색, Icon, Text의 세 단서 중 최소 두 개로 구분한다.

### 8.3 Progress / Recommendation Stepper

- 성취율보다 현재 단계와 남은 선택을 설명한다.
- `2/3`과 함께 단계 이름을 제공한다.
- 이전 단계 수정과 질문 건너뛰기를 허용한다.
- 완료하지 않아도 직접 탐색할 수 있다.
- Screen Reader에는 현재 단계와 전체 단계를 텍스트로 제공한다.

### 8.4 Option / Quiz Option 재해석

- 용도: 기록 방식, 시작 크기, 매체, 복귀 행동 선택
- 상태: Default, Hover, Focus, Selected, Recommended, Disabled/Unavailable, Error
- Recommended와 Selected를 구분한다. 추천은 시스템 제안, 선택은 사용자 결정이다.
- 선택 이유와 영향은 Option 아래 또는 결과 영역에 표시한다.
- Radio/Checkbox의 실제 의미에 맞는 단일·복수 선택을 사용한다.

### 8.5 Duration & Status

- 카운트다운과 압박 표현을 제거한다.
- `약 5분`, `지금 한 줄`, `나중에 이어도 됨`처럼 예상 부담을 설명한다.
- 시간이 지나도 실패 상태로 바뀌지 않는다.
- 실제 측정·성능 보장처럼 보이는 수치는 사용하지 않는다.

### 8.6 Card

Card 유형을 목적에 따라 구분한다.

| 유형 | 필수 정보 | 행동 |
|---|---|---|
| Method Card | 방식명, 적합 조건, 장점·제약 | 비교·상세 보기 |
| Recommendation Card | 추천 결과, 이유, 수정 가능성 | 이 방식으로 시작·다시 선택 |
| Record Start Card | 입력 유형, 예상 부담, 현재 지원 범위 | 시작 |
| Recovery Card | 중단 맥락, 보존 상태 | 지금 하기·보류·나누기·새 기록 |
| Status Card | 상태, 영향, 보존 범위 | 재시도·비교·도움 |

모든 정보를 Card 안에 넣지 않는다. 브랜드 이야기, 긴 설명, 대표 이미지는 Editorial Section으로 분리한다.

### 8.7 추가가 필요한 컴포넌트

기존 13장에 없지만 웹디자인 기능을 위해 규칙이 필요한 항목이다.

- Header/Navigation: 현재 위치, Mobile Menu, Skip Link
- Tab/Segmented Control: 기록 유형 전환과 Panel 연결
- Input/Textarea: Label, Help, Error, Character/Scope 안내
- Accordion/Disclosure: 비교 근거와 제한 정보
- Inline Alert/Status: 저장·보존·오류·미지원 안내
- Dialog/Drawer: 원본 영향이 있는 확인에서만 사용
- Empty State: 비난 없는 시작 안내와 직접 행동
- Comparison Row/Table: 동일 기준·동일 순서·Mobile Stack 규칙

| 상태 | 메시지 내용 | 시각 처리 | 행동 |
|---|---|---|---|

| SELECTED | 사용자가 고른 값 | Selection Surface+Check | 수정 |
| RECOMMENDED | 추천 초안과 이유 | 별도 Label, 선택과 구별 | 적용·다시 선택 |
| PENDING | 완료 여부 미확정 | Spinner만이 아닌 문장 | 기다리기·재시도 |
| ERROR | 실패한 행동과 보존 범위 | Danger+Icon+Inline | 오류 위치에서 복구 |
| LOCAL | 현재 기기 범위의 임시 상태 | 중립/정보 Badge | 범위 이해 |
| CONFLICT | 다른 버전 존재 | Warning+비교 정보 | 직접 선택 |
| HOLD | 현재 제공하지 않음 | Muted가 아닌 명료한 제한 | 대안 보기 |

### 9.1 상태 카피 공식

`무슨 일이 있었는지 → 무엇이 유지되는지 → 지금 할 수 있는 행동`

예시:

- 좋지 않음: `저장 실패`
- 권장: `이 기록은 아직 저장되지 않았습니다. 입력한 내용은 이 화면에 남아 있습니다. 다시 시도하거나 텍스트를 복사할 수 있습니다.`

## 10. Pattern과 사용자 흐름

### 10.1 방식 찾기

```text
목적 선택
→ 시작 부담 선택
→ 매체 조건 선택
→ 추천 초안 + 이유
→ 적용 / 답 수정 / 직접 탐색
```

- Progress는 시험 점수가 아니라 위치 안내다.
- 추천 결과는 자동 확정하지 않는다.
- Back 이동 시 기존 답을 유지한다.
- 질문을 건너뛰어도 핵심 콘텐츠에 접근할 수 있다.

### 10.2 작은 기록 시작

```text
한 줄 / 사진 / 음성 / 기분 선택
→ 지원 범위 확인
→ 입력 또는 프로토타입 행동
→ Inline 상태
→ 이어 쓰기 / 종료
```

- Tab 전환 시 작성 중 입력의 유지 여부를 알린다.
- 실제 업로드·녹음·클라우드 저장으로 오해시키지 않는다.
- 빈 입력, 입력 중, 보류, 오류 상태를 구분한다.

### 10.3 원본과 사본

```text
구조 미리보기
→ 표현 미리보기
→ 적용 영향 설명
→ 사본에 적용 / 취소
```

- Preview, Original, Copy를 Label로 명시한다.
- 취소해도 원본이 유지됨을 확인 행동 전에 설명한다.
- 최신 버전이나 추천안이 자동으로 원본을 덮어쓰지 않는다.

### 10.4 중단 후 복귀

- `밀린 기록 완료`를 기본 CTA로 두지 않는다.
- 지금 하기, 보류, 작은 단위로 나누기, 새 기록을 동등하게 제공한다.
- 연속일, 실패, 게으름, 완벽함을 카피에 사용하지 않는다.
- 사용자가 선택한 복귀 방식은 언제든 바꿀 수 있다.

## 11. 반응형·접근성 명세

### 11.1 Responsive

| 항목 | Desktop | Tablet | Mobile |
|---|---|---|---|
| Header | 전체 Navigation | 축약 Navigation | Menu Button+Drawer |
| Hero | Split/Asymmetric 가능 | 비율 축소 | 텍스트→이미지 단일 흐름 |
| 비교 | 2~3열 | 2열 또는 Scroll 보조 | 항목별 Stack, 같은 비교 순서 |
| Option | 2~4열 | 2열 | 1열, 전체 폭 |
| Editorial | Overlap 허용 | 겹침 축소 | 의미 순서 유지, 겹침 제거 |
| CTA | Inline | 필요 시 Wrap | 주요 CTA 전체 폭 후보 |

Horizontal Scroll은 콘텐츠 이해가 유지되는 경우에만 보조적으로 허용하고, 핵심 비교를 가로 스크롤에만 의존하지 않는다.

### 11.2 Accessibility

- Skip Link와 의미 있는 Landmark를 제공한다.
- Keyboard 순서는 시각 순서와 일치시킨다.
- `:focus-visible`을 제거하지 않는다.
- Tab, Radio, Accordion은 WAI-ARIA 패턴과 실제 키보드 동작을 맞춘다.
- 상태는 `aria-live`를 남용하지 않고 중요한 비동기 결과에만 사용한다.
- 모든 조작 영역은 최소 44×44px를 목표로 한다.
- 이미지에는 목적에 맞는 Alt를 제공하고 장식 이미지는 빈 Alt를 사용한다.
- 200% Zoom과 320px 폭에서 정보와 행동이 손실되지 않아야 한다.
- Reduced Motion에서도 같은 콘텐츠와 기능을 제공한다.

## 13. 우선 적용 순서와 의존성

```text
1. 기능 범위·상태 모델 확정
→ 2. Color·Typography·Spacing 확정
→ 3. Button·Badge·Option·Status
→ 4. Stepper·Comparison·Record Start
→ 5. Card와 Editorial Section
→ 6. Responsive·Accessibility
→ 7. Motion
→ 8. 13장 및 웹디자인 대조 검수
```

Motion과 장식은 마지막 단계다. 상태와 키보드 동작이 불완전한 상태에서 시각 효과를 먼저 확정하지 않는다.

### 13.1 최종안에서 차이를 보여줄 우선 3장

1. Colors: 브랜드색과 기능 상태색 분리
2. Quiz Option 또는 Progress: 추천·선택·단계 기능의 명확화
3. Card: 기능 Card와 Editorial Section의 역할 분리

Typography와 Radius & Effects는 위 3장의 Foundation 근거로 함께 갱신할 수 있다.

## 14. 검증 매트릭스

| 검증 영역 | 질문 | 통과 조건 |
|---|---|---|
| 브랜드 | 차분함과 선택 자율성이 보이는가 | 압박 카피·강제 흐름 없음 |
| 기능 | 첫 행동과 다음 행동이 명확한가 | 주요 과업을 설명 없이 수행 가능 |
| 추천 | 추천과 사용자 선택이 구분되는가 | Recommended/Selected 상태와 수정 행동 존재 |
| 보존 | 원본·사본·임시 상태를 이해하는가 | Label, 영향, 행동이 함께 표시 |
| 상태 | 정상 외 상태가 설계됐는가 | Empty/Pending/Error/Local/Conflict/Hold 포함 |
| 시각 | 개성과 정보 구조가 함께 유지되는가 | 브랜드 영역은 기억점, 기능 영역은 예측 가능 |
| 반응형 | 작은 화면에서 순서가 유지되는가 | 320px에서 잘림·행동 손실 없음 |
| 접근성 | 비마우스·저시력·모션 민감 사용자가 가능한가 | Keyboard, Focus, Contrast, Zoom, Reduced Motion 통과 |
| 범위 | 미지원 기능을 실제처럼 보이지 않게 했는가 | PROTOTYPE/HOLD와 대안 명시 |

### 14.1 사용자 평가 질문

초안 검토에서는 “예쁜가”만 묻지 않는다.

1. 첫 화면에서 이 사이트가 무엇을 돕는지 알 수 있는가?
2. Analog와 Digital 중 무엇을 선택해야 하는지 비교하기 쉬운가?
3. 추천을 그대로 따르지 않고 바꿀 수 있다는 점이 보이는가?
4. 가장 부담 없이 시작할 수 있는 행동이 무엇인지 보이는가?
5. 저장·원본·사본·보류 상태를 오해할 가능성이 있는가?
6. 감성적인 Section과 기능적인 Section이 하나의 브랜드처럼 느껴지는가?
7. 가장 마음에 드는 요소와 불편하거나 과한 요소는 무엇인가?

## 15. 오적용 방지 규칙

1. 레퍼런스의 색, Layout, Illustration, Copy를 그대로 복제하지 않는다.
2. Behance 콘셉트의 기능을 실제 운영 기능으로 간주하지 않는다.
3. GDWEB 정적 캡처만으로 Hover, Focus, Search, Reservation 동작을 확정하지 않는다.
4. 대형 기업·커머스의 기능 수를 DAMORI MVP에 그대로 넣지 않는다.
5. 감성적이라는 이유로 대비, Hit Area, Focus를 약화하지 않는다.
6. 모든 Section을 Rounded Card로 만들지 않는다.
7. 모든 기록을 성취, 연속일, 완료율로 표현하지 않는다.
8. Olive/Sage/Clay를 의미 상태색과 혼용하지 않는다.
9. 마스코트, Texture, Motion이 정보와 행동보다 먼저 인지되지 않게 한다.
10. 최종 Font, Logo, Slogan, 상품 사양과 실제 저장 기능을 확정 정보처럼 쓰지 않는다.

## 16. 산출물 적용 체크리스트

### 스타일가이드

- [ ] 13장의 Token과 Component 값이 서로 연결된다.
- [ ] 각 컴포넌트에 Anatomy, Variant, State, Usage, Do/Don't가 있다.
- [ ] DAMORI 예시는 실제 MVP 범위 안에 있다.
- [ ] Brand와 상태색이 분리된다.
- [ ] Responsive와 Accessibility 규칙이 포함된다.

### 웹디자인

- [ ] Hero가 목적·선택권·첫 행동을 설명한다.
- [ ] 추천은 이유와 수정 행동을 제공한다.
- [ ] 작은 기록의 지원 범위를 명시한다.
- [ ] Analog와 Digital을 동등하게 비교한다.
- [ ] 원본과 사본을 구분한다.
- [ ] 복귀 흐름이 사용자를 평가하지 않는다.
- [ ] Inline 상태와 복구 행동이 있다.
- [ ] Desktop·Tablet·Mobile에서 시각 QA를 완료한다.
- [ ] Keyboard·Focus·Reduced Motion을 검수한다.

## 17. 완료 판정

이 문서를 기준으로 한 수정안은 다음을 모두 만족할 때 완료로 본다.

1. 레퍼런스에서 가져온 각 원리가 DAMORI 사용자 문제와 연결된다.
2. 시각 표현과 기능 구조가 별개 목록이 아니라 같은 시스템으로 설명된다.
3. 정상 화면뿐 아니라 중단·오류·보류·충돌·미지원 상태가 정의된다.
4. 13장 수정 내용이 실제 웹디자인의 Pattern과 연결된다.
5. 적용하지 않은 레퍼런스 요소와 그 이유가 설명된다.
6. 초안 검토 후 최소 3개의 명확한 변경 근거를 최종안에 남길 수 있다.

### 최종 도출 문장

> DAMORI의 차별성은 장식의 양이 아니라 사용자가 자신의 기록 방식을 이해하고, 작은 단위로 시작하고, 중단 뒤에도 부담 없이 돌아오며, 현재 상태와 보존 범위를 오해하지 않게 하는 경험에서 나온다. 스타일가이드는 이 경험을 차분한 Editorial 표현과 명료한 기능 컴포넌트로 일관되게 구현해야 한다.
